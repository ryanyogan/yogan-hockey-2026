## The site on TanStack Start (#187 to #193, #196, #203; ADR 0009)

The site is TanStack Start, rendered on the server and hydrated, with no placeholders: a route's loader waits for everything its page draws. The sections from here to "Agate, the whole of it" are what the port learned, by subject, with the ticket a note came from in parentheses. The older sections below them have been brought up to date where they named something the port replaced.

- **The versions that work together** (#187): `cf` 1.0.0-beta.14 with `@cloudflare/vite-plugin` 2.0.0-beta.sha-91c870c02 (both pin `@cloudflare/config` 0.24.1), `@tanstack/react-start` 1.168.61, `@tanstack/react-router` 1.170.42 (router-core 1.171.35), vite 8.3.0. In `vite.config.ts`, `cloudflare({ viteEnvironment: { name: "ssr" } })` comes before `tanstackStart()` and `viteReact()`. `worker.ts` is the entry `cf` imports: it re-exports the Agents, routes `/agents/*`, answers the 308s and hands the rest to `@tanstack/react-start/server-entry`. Nothing had to be worked around. The Agents stay `exports` in `cloudflare.config.ts`; never add a `migrations` list.
- **A 500 on the first request after adding a dependency** ("Cannot read properties of null (reading 'useContext')") is Vite re-optimising mid-run and loading React twice. Restart the dev server (#187).
- **Dev runs effects twice** (Start's client entry is in `StrictMode`), so Favorites asks twice when `/players` is opened by a link in `pnpm dev`. A build asks once (#190).
- **Two exceptions to the letter of ADR 0009, both deliberate** (#187). The root route's loader data never goes stale by itself (the Scoreboard is the socket's after first paint, so the dateline's record of the picks is read again only when `invalidatedAt` moves). And `/nhl`'s input schema, `NhlPageSchema`, is in `apps/web/lib/nhl-page.ts` beside the tabs it validates, built on `StandingsViewSchema` from `packages/schemas`.
- **Two navigations in quick succession** (back pressed twice) made an uncaught "AbortError: Transition was skipped" on the page: the browser rejects the skipped transition's `ready`, and the router keeps only `updateCallbackDone`. `lib/skipped-transition.ts` wraps `document.startViewTransition` once, from `getRouter`, and handles that rejection alone (#187).
- **`Link` adds `data-status`, `aria-current` and an `active` class** to any link to the open page. The markup was frozen for the port and the components set `aria-current` themselves, so `components/link.tsx` builds its anchor with `useLinkProps` and strips all three (#187).
- **The string `getAgentByName` in the browser's script is `agents/react`'s own** (a `console.warn` about an identity changing on reconnect), not server code. `cloudflare:workers`, the ESPN host, cachified and drizzle are not in it (#187).
- **What the lockfile still names** (#187, #193). `@vitejs/plugin-rsc` and `react-server-dom-rspack` are there only as optional peers of `@tanstack/react-start` and its `react-start-rsc`; neither is installed. `next` is there as a peer dependency of `geist`, which `scripts/app-icons.ts` reads one font file from; no file imports `next`. `next-themes` is a separate package, which the site uses.
- **A file's `"use client"` directive meant nothing to the build**: removing all 27 changed no chunk beyond rounding (#193).
- **knip finds nothing left over** (#193): `pnpm dlx knip` with `worker.ts`, `cloudflare.config.ts`, `agents/test-worker.ts` and `src/routes/**` given as entries reports no unused file and no unused dependency but `tailwindcss`, which is a false positive (it is imported from CSS).

## Routes, loaders and server functions

- **Where a page is.** A route is a file under `apps/web/src/routes/`; its loader calls one server function in `src/functions/`, which wraps a read in `lib/` (`src/functions/team.ts` wraps `lib/team-read.ts`, `src/functions/game.ts` wraps `readGamePage` in `lib/game-page.ts`). A server function's validator is the site's schema for the thing (`GameSchema.pick({ id: true })`), and what is a 404 and not a fault is told apart after it, by `findGame` or `findTeam` (#188, #189).
- **A file in `src/routes/` is a route unless its name starts with `-`.** A test beside a route is `-picks.test.ts`, or the generator takes it for a route and the build warns that it exports no `Route`. `src/team-routes.test.ts` and `src/game-routes.test.ts` sit beside the directory for that reason (#188, #192).
- **A route's component must not import a module that imports `cloudflare:workers`, even for a constant** (#192). The browser fetches the route's file, then `lib/kv-cache.ts`, which answers 500 in dev, and the page falls to the error page after it had been drawn whole by the server: the HTML is right and the hydrated page is wrong, so `curl` does not show it. `/skeleton` wanted `SKELETON_AGENT_NAME` from `lib/skeleton.ts`; its server function returns the name instead. A server function's handler and what only it imports are taken out of the browser's script, so the sample slates (`lib/sample-slate.ts`, `lib/agate-slates.ts`) are not in it either. Checked on a build: none of `cloudflare:workers`, the ESPN host, drizzle or a sample venue's name is in `assets/*.js`.
- **What a server function returns must be serializable in its type** (#189): `Record<string, unknown>` is refused by the compiler ("Type may not be serializable"), which is how a Prediction's `inputs` (everything the model was given) was caught on its way to the browser. A loader's data is sent whole, so `readGamePage` drops `inputs` (`PagePrediction`). Look at what a read returns, not only at what the page draws.
- **The router writes a loader's error into the page's HTML**, message and all (`e:new Error("ESPN https://site.api.espn.com/... could not be fetched")` in the dehydrated state), in a production build too, and answers a navigation's server function with the same. Every page-level read goes through `pageRead` (`src/functions/page-read.ts`), which notes the failure for the status, logs it, and throws a sentence that says nothing. A server function that reads ESPN without `pageRead` leaks (#187).
- **The calls made outside a loader**: resolving favorites (`resolveFavoritePlayers` in `src/functions/favorites.ts`, called from `useFavoritePlayers`), `readReplayPlays`, which `FinishedGame` asks for a game that ended on an open page, and the sample pages' two writes. The pick has no write on the site: a Prediction is made by the Scoreboard Agent, and the page learns of it when `invalidatedAt` moves and the game's loader runs again (#189, #191).
- **A form that calls a server function is `onSubmit` with `preventDefault`**, and has no `method`: pressed before the page has hydrated it is a GET of the page with the button's name in the query, which does nothing and leaves the page where it was, so a script that presses again (`e2e/picks.setup.ts`) succeeds. With `method="post"` the early press would be a POST of the page (#192).
- **`throw redirect({ href })` in a server function moves the page** when the function is called through `useServerFn`: `seedPicks` ends at `/skeleton/picks?seeded=right`. `router.navigate({ href })` from a script loads a document; `router.history.push(href)` does not (#192).
- **A server function called from an event handler that rejects is nobody's**: no error page, only an unhandled rejection. `useFailure` (`components/skeleton/use-failure.ts`) throws it on the next render, so it reaches the route's error page. The redirect `seedPicks` throws is not a rejection there (#192).
- **A method a server route has no handler for is answered with the site's page, a 200 of HTML**, not a 405. `/picks` (`src/routes/picks.ts`) answers the others itself, as its address did before the port: a bare 405 to POST, PUT, PATCH and DELETE, and 204 with `Allow: GET, HEAD, OPTIONS` to OPTIONS. HEAD is answered from GET. On the dev server Vite's own CORS answers OPTIONS before the route does, with no `Allow` (#192).
- **Home's first load reads the Scoreboard and the season's record more than once**: the root's server function and Home's are separate calls and nothing joins them. Left as it is (#191).

## Parent routes and tabs

- **A page with tabs is a directory** (#188): `src/routes/nhl/teams/$id/route.tsx` is the parent (its loader reads the team; its component draws the header, the tab bar and `<Outlet />`), and `index.tsx`, `roster.tsx` and `stats.tsx` beside it are the tabs, each with a loader and a server function of its own.
- **A game is one read and its tabs have none** (#189). `src/routes/nhl/games/$id/route.tsx` reads the game with `readGameRoute` (the Game Agent's answer, a finished game's plays from D1, the pick, a scheduled game's matchup facts) and draws all of it. `index.tsx`, `scoring.tsx` and `pick.tsx` beside it are empty routes: a tab is the same game drawn another way, and `GameView` reads which from the address (`lib/use-page-address.ts`). Only the tabs subscribe to the address, so changing tab does not reset the playhead, the selected play, the transport or the socket (#107).
- **A player's route reads everything both tabs draw** (`readPlayer`: profile, season, career and the whole game log as views), and `index.tsx` and `games.tsx` have no loader: `PlayerGames` takes the log from `getRouteApi("/players/$id").useLoaderData()` and the default tab shows its first ten. Going between the tabs makes no request of any kind, which `e2e/players.spec.ts` asserts (#190). In a short recorded season the full log still offers "show latest", so its default is reachable (#107).
- **Changing tab asks for the tab alone, however old the parent's read is** (#188, corrected in #189). The router reads a stale match again when it is entered, or when the same address is loaded again; a parent kept across a change of tab is stayed on, so its age is never looked at (router-core 1.171, `load-client.ts`). `src/team-routes.test.ts` and `src/game-routes.test.ts` run the routes with a stale time of zero and count: the tab is asked for and the parent is not; a tab gone back to is entered, so it is read again once its own read is past five minutes. So "changing tab makes no request for the game" needs no `shouldReload` and no stale time.
- **A parent route with a `notFoundComponent` is also handed every address beneath it that no route answers** (`/nhl/teams/21/coaches`, `/nhl/games/401803652/coaches`): the router marks the parent's match `_notFound`, the parent's component is drawn as if all were well, and its `<Outlet />` draws the parent's `notFoundComponent`. Left alone that is "Team not found" under Toronto's header. So the component tells the two apart by its match's `status` ("notFound" only when its own read threw) and the parent draws its outlet alone when `_notFound` is set: the site's not-found page, by itself. The team's and the game's routes both do it; another parent with tabs needs the same (#188, #189).
- **A tab whose read failed takes the header with it**: the parent's component asks `useChildMatches` whether a tab's match is an error and then draws its `<Outlet />` alone. Left to the router, the error page would stand under the team's header and tabs (#188).

## Not found and failure

- **The error page is `ErrorPage`** (`components/shell/error-page.tsx`, the router's `defaultErrorComponent`), one for the whole site, drawn inside the shell where the page would be. Its words and its way back come from the path (`unreadPage` in `lib/error-page.ts`): a team leads to the teams, a player to the search, a game to the live scores, the rest to tonight. It never prints the error. A page that catches its own failed read keeps doing so (Home's standings, the player search, the game page's `unreadable`, the picks); a read that throws lands here. In fixture mode `/nhl/teams/1` and `/players/1` are it (#84). Its retry is `router.invalidate()` inside a transition: the failure is in what the loader read, so it is read again.
- **Statuses** (#187). Start answers a page whose loader threw with 500 and draws the error page inside the shell. The Worker's entry runs each request in `answerWithRenderStatus`: `pageRead` calls `noteRenderFailure`, and an ESPN failure (`EspnFetchError` or `EspnParseError`) turns the 500 into a 503. Those two are all `lib/render-failure.ts` exports (#193). The AsyncLocalStorage store reaches a server function called by a loader during the server's render. Seen on a build under `vite preview`: 503 and 500 with `cache-control: no-store`, the title "Not answering", the error page inside the shell; an unknown address 404 with "Not found". Only a whole page is touched: a navigation inside the site asks for a server function's answer, and the router draws the error page from it.
- **The page of last resort** is written out whole in `lib/render-failure.ts` (no stylesheet to count on) and answered with a 500 when Start could not answer a request at all. Under the wordmark's double rule its title has no heavy rule of its own: three heavy rules in 40px read as a fault (#84, #173).
- **A route's title is `titled(match, title)` (`src/head.ts`), and no component renders a `<title>`** (#187). The router calls `head` for the match whose read failed and for none beneath it, with `match.status` `"error"` or `"notFound"`; for an address no route answers it marks the root's match `_notFound` (the field is `_notFound` in router-core 1.171, not the `globalNotFound` older documentation names, and it has no public name). A `<title>` in the error or not-found component makes two in the document and the browser shows the first. After a router upgrade, `e2e/shell.spec.ts` (the not-found page's title) says whether the mark still holds.
- **A title under a parent route** (#188): `titled(match, title, "Team not found")` gives a route's own words for its not-found page, and a tab's `head` is `failureTitled(match)`, which says nothing while the tab's read answers (the parent's title stands) and "Not answering" when it does not. A tab with a `head` that always returned a title would replace the team's name. The player's `head` is called with `status: "notFound"`, which is where "Player not found" is titled (#190).
- **`notFound()` thrown inside a server function reaches the route that called it**, on a first load (404, the route's `notFoundComponent` inside the shell) and on a navigation in the browser (tried with `router.navigate` to `/nhl/games/not-a-game`: no document load, the page and its title are the not-found page's) (#189, #190).
- **Each read of a team's page answers "not found" itself** (`pageNotFound()` in `lib/team-read.ts`): the parent's loader and the tab's run side by side on a first load. The parent route's `notFoundComponent` is "Team not found" and stands where the parent's component would. The same goes for a failure: the route that threw is the one replaced (#188).
- **Rylan has no page**: `/family/rylan`, `/yogan`, `/players/rylan-yogan` and `/players/easter-egg-rylan-yogan` are 404s, which `e2e/shell.spec.ts` asserts (the fictional player was retired by #99, `lib/players.test.ts`). There is no 308 for his Parity Reference address, though #187 names one (#187, #190).

## Freshness: what is read again, and when

- **The router's defaults are not ADR 0009's** (#187). Its `staleTime` default is 0 (every visit reads again) and its preload stale time 30 s. `src/router.tsx` sets both to five minutes. The root route's is infinite, so the Scoreboard and the season's record are read again only by `router.invalidate()`, which the socket calls when `invalidatedAt` moves (`lib/use-refresh-on-invalidation.ts`). `e2e/nhl.spec.ts` proves it: the page's own state on the socket runs no loader, a later `invalidatedAt` runs the root's and the page's once each.
- **A route that is stayed on is not read again because its read got old** (#189). Only `router.invalidate()` reads it again, which is what a final or a pick causes. So a visitor who stays on one team's tabs keeps the header and the slate's picks as first read until the Scoreboard says a read is out of date (a final or a catch-up), the address is loaded again, or the team is left and come back to after five minutes (#188).
- **After a server function that wrote something, `router.invalidate()` reads the page again** (`/skeleton`'s bump). It runs the root's loader as well (#192).
- **A read that said "not answering" is the one read the router must not keep, and `shouldReload` is not handed the answer** (only `deps`, `params` and the cause). A loader's data is good for five minutes whatever it says, and the first page's read is the server's, so the browser has to remember for itself. The game's page that says "could not be read just now" notes its game in the browser (`unread` in the route file) and `shouldReload` reads that game again on the way back; `router.invalidate({ filter })` from an effect's cleanup was tried first and read the game on the way out and twice on the way back (#189). The players' search does the same for its searches (below).

## The cache of ESPN reads on KV

- **cachified's KV adapter is the site's own** (`lib/kv-cache.ts`, forty lines). The published one, `cachified-adapter-cloudflare-kv`, was last released in September 2024 against workers-types 4. KV refuses an `expirationTtl` under 60 s, so the adapter never asks for less (#187).
- **Nothing is tagged: a final deletes a fixed set of keys** (`forgetStandings`, `forgetTeams`, `forgetPlayers`, `forgetGame` in `lib/espn.ts`). Nothing forgets the team list but its 24-hour limit, as the spec's cache table says: `forgetTeamList` had no caller and was removed (#187, #193).
- **A stale answer is kept thirty days** (`STALE_FOR` in `lib/kv-cache.ts`): the first visitor after a quiet stretch is answered with what KV has and the next with what ESPN has. A refresh already on its way when a final forgets a key can write the older answer back; the Scoreboard Agent's second round five minutes on covers the standings and the teams (#187).
- **A forgotten key is read before it is answered**, so after a final the first visitor to each of the two teams' pages waits on ESPN. The Scoreboard could read the team and schedule again after forgetting, which would hide it; not done (#94).
- **The KV entry is `{ value, metadata: { ttl, swr, createdTime } }` under a plain key** (`skeleton-reading`, `espn-standings`), in the namespace the explorer calls `CACHE-yogan-hockey` (#192).
- **KV refuses a second write to one key within a second.** Seen before the port, when one key held every invalidation time and two finals in one poll wrote it twice (#95).

## Search parameters are text, and the players' search (#190)

- **A query string is text, on every route** (`lib/search-text.ts`, set as `parseSearch` and `stringifySearch` in `src/router.tsx`). The router's own way is JSON: `?q=99` was the number 99 and was written back as `?q=%2299%22`, `?q=1e3` searched for "1000" and `?q=true` was a boolean. Now a value is the string the address spells, a parameter given twice is a list of strings, and what is read is written back as it was. So a search parameter is always a string or a list of strings, never a number or a boolean, in `loaderDeps`, `validateSearch` and `useSearch` alike; `Link` and `navigate` take `search` values as strings. `/nhl`'s `tab` and `view` answer as before (`lib/search-text.test.ts`, `e2e/nhl.spec.ts`).
- **The search box navigates; it does not fetch.** Each pause in typing is `navigate({ to: "/players", search: { q }, replace: true, resetScroll: false, viewTransition: false })`, and the loader keyed on `q` does the asking. Without `viewTransition: false` every keystroke's answer would cross-fade the page (`defaultViewTransition`). The results drawn are the loader's; a box shorter than two characters draws nothing at once without waiting for the address.
- **The box tells its own navigations from a link's by remembering what it last put in the address** (`sent`), and reads the address from `state.location`, which is the one being gone to. `Route.useSearch()` and `lib/use-page-address.ts` both give the address of the page that is drawn, which lags a search still being read: compared with what is typed, either would empty the box under the visitor's fingers. It reads it only while the address is `/players`: a tap on a result moves `state.location` to the player at once, and without the check the box and the results emptied on the page being left (seen with the player's read held for two seconds).
- **A search that was not answering is not kept; every other answer is fresh for five minutes like any route's.** `searchLoading` (`lib/player-search.ts`) remembers, in the browser, the searches last answered "not answering", and `shouldReload` returns true for those and `undefined` (the router's own rule) for the rest. The answer in a document's HTML never went through the browser's loader, so the page tells the loading of it in an effect (`loading.drawn`). The loader is `{ handler, staleReloadMode: "blocking" }`: left at the default, a search asked again would show its old "not answering" first and the answer after. `staleTime: 0` was tried first and dropped (every search asked again on every visit). Two others were set aside on a reading of the router, not a run: throwing so that nothing is cached (the route's `errorComponent` takes the component's place, so the box would be remounted) and `router.invalidate` with a filter (it reads the match again at once).
- **A search whose call fails reloads its address when the browser is on line**, for both failures a stale tab can meet (see "A tab older than the deploy"): they can be told apart only by the text of the framework's error. Seen in that experiment: the renamed function's old tab made one document request for `/players?q=mar` and showed the new build's ten results (the box's focus is lost); the throwing handler's made one document request, which was the error page under a 500, and no more in the four seconds after. It cannot go round, because a document's search is read on the server with no call to fail, and a page only being read ahead is never reloaded. Off line the search says "Search is not answering. Try again shortly." with the box, its text and its focus kept (proved against a real router in `lib/players-loading.test.ts`).

## Hydration, and what `__APP_HYDRATED` means (#203)

- **The shell hydrates first and the page under the masthead a moment after.** The router draws the root route's child inside a `<Suspense>` of its own (`Outlet` in `@tanstack/react-router` 1.170.42, `Match.js`), and React hydrates what a boundary holds in a later pass, once the route's script is in. Measured on `/players?q=mar`: when the root's effect sets `window.__APP_HYDRATED` the masthead's links have hydrated and the search box has not; the box follows 75 to 100 ms later in `pnpm dev` and 23 to 35 ms later on a build under `vite preview`. So `__APP_HYDRATED` says the shell has hydrated and a link is the router's, not that the page has, and `__APP_HYDRATED_AT` is early by that much.
- **A link followed inside that moment makes React report a hydration error**, in dev "Hydration failed because the server rendered text didn't match the client" and on a build "Minified React error #418": the router has moved on, so the boundary hydrates the HTML of the page left with the data of the page gone to, and React draws the new page afresh. The visitor sees the page he asked for; the console has the error. Nothing on a page that is only loaded differs from what the server drew. Left as it is: the boundary is the router's, and no public event of the router's or React's says the page beneath has hydrated (`onRendered` is acknowledged from `Matches`, outside the boundary).
- **A link pressed before the shell has hydrated is a new document**, and anything a script left in `window` is gone with the old one: wait for the flag, and put a time that must outlive the document in `sessionStorage` (#126). Marking a document before it hydrates has its own trap: React logs the mark as an attribute the server had not sent ("A tree hydrated but some attributes of the server rendered HTML didn't match the client properties", which it leaves in place). The masthead is kept across a navigation the router makes: after one, the banner is the same DOM node, with the mark on it.
- **The not-found page of an address no route answers has no boundary**: `Outlet` draws it for the root before it reaches its `<Suspense>`, so it hydrates with the shell and `shellHydrated(page)` is enough before a link is followed from it. After a hard load of a route's page, wait as well for something that page does only once hydrated (`e2e/players.spec.ts` waits for Favorites to stop being busy).
- **`scripts/measure-performance.ts` reads `__APP_HYDRATED_AT` as the time of hydration**, so its figure is the shell's and is early by the moment above. `scripts/tap-targets.mjs` waits on `__APP_HYDRATED` before it taps.

## A tab older than the deploy (#190)

- **A server function called from a tab older than the last deploy either works or throws; it never answers with nothing.** Found by running it, not by reading: `vite preview` of one build with `/players` open in a browser, the site rebuilt and the preview restarted under the open tab, then "mar" typed in the tab. Three second builds, and what the old tab received:
  - *Only client code changed.* A server function's address is `/_serverFn/<sha256 of its file and export name>`, which a build does not change: the call was answered 200 and the search and the favorites worked as if nothing had happened.
  - *The function renamed, so its address is one the server no longer has.* `500`, `content-type: application/json`, body `{"status":500,"unhandled":true,"message":"HTTPError"}`; the call rejects with an `Error` whose message is that body.
  - *The function still there, its handler throwing.* `200`, `application/json`, a serialised error (`"c":"$TSR/Error"`, the message `pageRead` gives, "The page could not be read"); the call rejects with an `Error` of that message.
  So a failed call is a `catch`, and no guard for an answer of `undefined` is needed. Not shown: a real deploy on Cloudflare (only local builds), and a function whose name stays while its input changes (its validator would throw, which should be the third case).
- **Favorites does not reload.** A failed `resolveFavoritePlayers` leaves every id asked for "unread" and the block says "Your favorites could not be read just now."; the ids are asked for again when the page is next opened (tried on the dev server by rewriting the request's address to a function id the server does not have, #191). Reloading for any failed call would go round for as long as the call kept failing, since Favorites asks again on every load. The search does reload (above).
- **An old tab that follows a link to a page whose script the deploy replaced recovers by itself**: the route's chunk is a 404, and the router loads the address as a document. Seen in the same experiment, going from `/players` to `/nhl`.

## Fonts (#168, #183, #187, #196, #193)

- **The fonts are the site's own files, not Fontsource's packages**: 22 files in `apps/web/public/fonts`, their faces in `apps/web/src/fonts.css`, the five Latin ones preloaded by `src/head.ts`, the family names "Newsreader" and "IBM Plex Sans Condensed". #187 asked for Fontsource and the first cut used it, and two things were wrong. Fontsource ships the hinted cut of IBM Plex Sans Condensed (`fpgm`, `prep` and `cvt` tables, about 19.8 kB a weight) and of Newsreader (`prep`), where the site had served Google's unhinted files (14.5 kB): version, glyphs, axes and advances are the same, and on Linux the hinted ones draw tracked capitals a pixel or two narrower a word (up to 5% at weights 600 and 700; a finished game at 390 was 5917px tall for 5959), which changed 4 to 7% of the pixels of each kept shot of `/nhl` and is not what #183 sized the fallback faces against. macOS, iOS and Android ignore hinting. And on a build the stylesheet kept Fontsource's relative `url(./files/...)` with no such files in the output, so every face but the five preloaded was a 404; `pnpm dev` did not show it. The 22 files are byte for byte the ones the site served before the port, and with them `agate-routes.mjs` shoots `/nhl` identical to the kept shots but for the dateline's record of the picks.
- **So the Agate scripts accept "Newsreader" and nothing else**, and `agate-home-compare.mjs` goes on fetching the prototype's fonts as a Mac, which is how it gets Google's unhinted files (the note on Google's two sets under "Agate 4: Home").
- **`node scripts/built-fonts.mjs` after a build** fails when a built stylesheet or the Worker's script (the preloads) names a font file the build does not hold. CI runs it after the dry run. `scripts/font-load.mjs` against a preview still exits 0 (#187).
- **A font file's name carries a hash**, so `public/_headers` serves `/fonts/*` as `immutable` for a year, as it does the team marks.
- **In `pnpm dev` Chromium warns of each of the five preloaded fonts that it "was preloaded using link preload but not used within a few seconds", on every page; a build does not** (`vite preview`: five font requests, no warning) (#193). ## The goal sequence (#142)

- **Where it is.** `lib/game/goal.ts` (pure: `goalSequence` is what the `goal` member of `RinkAnimation` carries besides its line, `goalCall` the caption's words, `goalTint` the team colour lifted for slate, gone in #173), the `goal` function in `rink-player.ts` (the steps after the shot lands), and in `rink.tsx` the lamps (`GoalLamp`) and the end zones (`EndTint`). The player rolls only when the figure already reads the goal's new score: if ESPN's header is a poll behind the play, nothing rolls and the figure changes when the header does.
- **Text the player shows is CSS `content`, not text nodes** ("GOAL" over centre ice, the score before): the smoke tests read `rink-status` and `rink-score` with `toHaveText`, which is `textContent`, hidden text included.

While the goal is the latest play, or a Replay's playhead is on it, it stays.
- **#141's rule, widened**: outside the drawing the player sets only `opacity` and `transform` (on the score's roll, the live marker, the caption's parts) and data attributes on elements React gives none. It never sets a property React sets, which is what the rule is for.

- **Known and left**: of two goals for one side in one poll, the first does not roll: the header already reads the second's score, so there is no true figure to roll to. The score stands at the first goal's from the moment its shot starts (held for the second), and the second rolls. A goal with no coordinate has no cue at all, so no sequence.

## Penalties and the power play (#143)

- **Two kinds of thing, drawn two ways.** The whistle is a cue like a shot (`describePlay`'s `penalty` member, `whistle` in `rink-player.ts`). Who sits and who has the advantage is a state that lasts minutes, so React draws it from `penaltyState` (`lib/game/penalties.ts`, pure): the box (`components/game/penalty-box.tsx`) and the ruled zone (`PowerPlayZones` in `rink.tsx`). Nothing of it is GSAP's, which is why a Replay's step, a reload and reduced motion all show it right with no code of their own.
- **ESPN records the penalty and nothing after it**: the team, the players (the penalized one first, no roles), the infraction as the play's type, `penaltyMinutes` and `penaltyType` on the type, and a `strength` on every play. No play says a penalty ended or who is on the ice. Everything else is the rule book, written out at the top of `penalties.ts`; change a rule there and in its table of cases together.
- **A goal's `strength` is the one check the data offers**: the tests hold the computed skaters against it for every recorded goal (one power-play, one short-handed). A penalty's own `strength` is the ice before the call, "even-strength" for all six recorded.
- **The recorded game has six minors and one power-play goal, scored the second the penalty ran out** (2nd 4:24, Greenway's from 2:24). So a goal counts a penalty as running through the second it ends, or that goal would be even-strength; and no recording has a goal cutting a penalty short, a double minor, a major, coincidentals or a carry across a period. Those are cases built from `play()` in the test, and scenes built in `scripts/rink-shots.ts`.
- **`penaltyMinutes` is in a play's `detail` JSON in D1, so it needed no migration**, and a game archived before #143 has none. Its box would stay empty, so `replayGame` reads such a game from ESPN again on its next open (`withPenaltyMinutes`): once, since the re-read writes the minutes.
- **A live header's clock is usually "0:00"** (see #50's notes), so the box counts down on `streamReading`'s `clock`: the header's when it has one, the Scoreboard's for the same game and period, else none. With none, and between polls with one, the countdown stands at the latest play's time. Nothing ticks in the browser: a game clock stops at every whistle and the page cannot know.
- **The box is always a heading and two rows (74px)**, under a rink with no game on it too (`PenaltyBoxSpace`), so a penalty moves nothing. A wide rink has two rows a team. More than that adds a row: seen only with three in the box on a phone.
- **A game is over for the box when the page says so**: `GameRink` shows nobody for a final game laid out whole, since a game just gone final may not have its `end-of-game` play yet. And the zone is ruled only when the period in focus is the one being played: pick a 1st-period tick in the 2nd and the ends on the ice are the 1st's.
- **A grid column needs `min-w-0` for `truncate` inside it to work**; without it the long infraction pushed the countdown off a phone's edge.
- (History: gone in #173, where the box and the ruling became ink.) **A team's colour as a mark is `teamColour` and `TEAM_BG`** (`components/game/team-colour.ts`): the colour as `--team`, lifted in the dark theme with `color-mix` in CSS, so nothing reads the theme in script. An SVG `<pattern>`'s line takes the class as any element does.
- **`node scripts/rink-shots.ts <url> docs/design/rink-animations penalties`** takes only the shots in `docs/design/penalties/` and prints the box at each scene and each Replay step. Its first run against a cold dev server times out waiting for the game view; run it again.
- **Sizes** from `ESPN_FIXTURES=1 pnpm build`: `game-page` 28.21 kB (9.52 gzip) before, 37.12 kB (12.53) after, about half of it the rules; `rink-player` 72.04 kB (28.35) before, 72.80 kB (28.51) after.

## The animated rink (#141)

- **Three parts.** `lib/game/rink-animation.ts` (`describePlay`: a play to a `RinkAnimation`, pure), `lib/game/rink-queue.ts` (a reducer: what the page shows to what the ice plays, pure) and `components/game/rink-player.ts` (GSAP draws one cue). `RinkAnimations` joins them and renders nothing. The goal sequence (#142) adds fields to the `goal` member and steps to its timeline; penalties (#143) added a member and a `case` in `timelineFor`, and reuse the save's ring.
- **The rules are the queue's**, the same for a Game Stream and a Replay: a page opening plays nothing; following a game, arrivals queue and play one at a time; a picked play (a Replay's playhead, a clicked tick) replaces whatever is on the ice, and clears it if it has nothing to draw; following a game, the last shot stays as it ended until the next arrives. One poll of ESPN is a burst (save, stoppage, faceoff arrive together), so a burst is the usual case, not the odd one.
- **GSAP only touches what React never changes**: the effects layer and the creases, which have constant props, and a dot's `transform`, which React does not set. A tween of a React-owned attribute (a dot's `r`) loses to the next render, or wins against it and leaves the wrong size.
- **GSAP rounds a style in px**, so `strokeDashoffset` from 1 to 0 on a `pathLength="1"` line jumps instead of drawing (the prototype's line has this fault). Tween the line's `x2`/`y2` with `attr`.
- **A `set` inside a timeline is not drawn until the next tick**, which is one empty frame between two cues. Set the starting state with `gsap.set` outside the timeline.
- **Reduced motion still holds each cue**: the timeline is jumped to its end, but the cue is reported finished only after the hold, or a burst would show only its last play.
- **The focused dot is keyed by its play.** Unkeyed, React hands the same `<circle>` to the next focus, with whatever a timeline had half done to it.
- **A page that had no plays and then has the game is opening, not watching**: the Game Agent's first message is every play so far. The queue plays nothing for it.
- **The cue effects are layout effects**, so a dot and a caption are hidden before the frame that would have shown them whole.
- **GSAP is one lazy chunk**, fetched when a game page first has something to play, and `rink-player.ts` is the only file that may import it. Sizes from `ESPN_FIXTURES=1 pnpm build`: `game-page` 23.67 kB (7.96 gzip) before, 28.21 kB (9.52) after; `rink-player` 72.04 kB (28.35), on first cue only; no other chunk changed. Compare the build log's chunk list before and after: the bytes a browser loads for a route vary by a few files from run to run with what gets prefetched.
- **The minifier drops every comment, licence notices included** (React's too). GSAP's licence wants its notice kept, so `apps/web/vite.config.ts` writes it back on the `rink-player` chunk with `output.postBanner`. Renaming that file means renaming `GSAP_CHUNK` there.
- **`node scripts/rink-shots.ts <url>`** retakes `docs/design/rink-animations/` and prints what was on the ice after each step of a Replay and a Game Stream, and the layout shift with and without animations (it blocks the chunk for the second). The recorded game has no shot without a coordinate, so the script makes one.
- **Layout shift cannot be told from a single number here**: stepping a Replay grows and shrinks the plays list, which Chrome counts when the click is scripted. So the script runs each case twice, animated and with the chunk blocked: Replay 0.4436 animated against 0.4503 without, Game Stream 0.1335 against 0.1362. The figures move by a few thousandths from run to run with when the list's rows land; the animations, which draw only inside the SVG and with transforms, add none.
- **`vite preview` has no plays for the recorded game** unless the fixture D1 is copied over (see "Local preview data matters" under #107), so the ticks are missing there; check animations on `pnpm dev`.

## The approved look (#138)

What was measured and the decisions taken: `docs/design/approved-look.md`.

- **The look's values are tokens in `packages/ui/src/theme.css`**, the approved prototype's. Text: `text-foreground`, then `text-note` (a note, an idle link, a second line), `text-label` (a column header, a count), `text-aside` (a record, a rank, the footer); never the foreground at an opacity. Rules: `border-border` under a row, `border-rule-head` under a column header, `border-rule` framing the shell. Sizes: `text-body` (13px on 20; 15 on 22 below `md`), `text-small` (11 and 12px on 16), `text-score` (16 and 20px), `text-wordmark`. Weights by what the text is: `font-quiet` 400, `font-body` and `font-label` 500, `font-strong` and `font-score` 700. Spacing is Tailwind's steps 1, 2, 3, 4, 6, 8 and 12 (4 to 48px) and `py-row`, a ledger row's own padding (6px; 11px on a phone). The sizes change at 767.98px in the stylesheet, so a class never needs a phone variant to get the larger type. (#168 changed the colours, the face and two weights: see "Agate 1" at the end.)
- **A token that looks like another kind of utility must be named in `packages/ui/src/cn.ts`.** `cn` is tailwind-merge's rules: to it `text-small` and `text-label` were both colours and the later one silently removed the earlier, so column headers lost their colour and a losing score its size. The package's own `cn` (`../cn`, tested) is told which names are sizes, weights, spacing and tracking; add a new one there, and never import `cn` from `"cn"` in a component.
- **Every ledger row is one height**: 33px, 45px on a phone, and a game's row 55px there (two lines and 8px, `GAME_TEXT_CELL` and `GAME_SCORE_CELL` in `game-ledger.tsx`). `Ledger`'s `density="compact"` is gone. A placeholder gets a cell's own padding through `SkeletonColumn.cellClassName`, which is not put on the header as `className` is.
- **Tabs on a phone are a ruled strip of 44px cells** (`UrlTabs`). A set of choices that is not links wears the same with `tabStrip` and `tabCell` from `url-tabs.tsx` (the game page's key-plays radios do).
- **A grid that goes to two columns at `xl` needs `grid-cols-1` below it**, or its one implicit column is as wide as the widest ledger and the page scrolls sideways on a phone. The larger phone type found three that lacked it.
- **A team's mark is 1.2em**, so 18px on a phone: `teamMarkImages` gives 28, 42 and 84px files for 1x, 2x and 3x at every size.
- **`node scripts/font-load.mjs <build's URL>` measures the font swap by holding the font files back.** `vite preview` has no plays in its D1, so a game's page there has no rows: the script measures the page's blocks as well as a ledger row, and fails rather than report 0px for nothing measured. (The face of #138 was Geist Mono; #168 replaced it: see "Agate 1".)

## Running things

- **Ports.** The dev server is pinned to `PORT` (default 5173) with `strictPort`. Parallel worktrees each use their own `PORT`; the orchestrator assigns it. Stop strays before Playwright, which reuses whatever answers on its port.
- **Set `TMPDIR` to a directory on disk before running anything**: `export TMPDIR="$PWD/node_modules/.tmp" && mkdir -p "$TMPDIR"`. `/tmp` on this machine is a small tmpfs with a per-user quota, shared by every worktree, and the dev server, Vitest and Playwright fill it. The symptoms look like code faults and are not: `Unknown system error -122` in Vitest, `net::ERR_INSUFFICIENT_RESOURCES` or `Failed to fetch dynamically imported module` in Playwright.
- **Killing strays.** Stop your own dev server by its port: `fuser -k -n tcp <PORT>` (this machine has no `lsof`, and a script that kills by `lsof` output kills nothing and says nothing). `pkill -f` is not scoped to your worktree, so it can kill another subagent's server, and a pattern that appears in your own command line kills your shell.
- **`cf d1 migrations apply --local` fails to exit about half the time** (cf 1.0.0-beta.12). `apps/web/scripts/migrate-local.sh` retries it; call that, never the bare command, in anything Playwright or CI waits on.
- **`cf d1 migrations apply` accepts only a database id**, and `bindings.kv()` only an id. The real ids live in `apps/web/cloudflare.resources.json`. Local dev uses neither: it keys its simulated D1 by `LOCAL_D1_ID` in `apps/web/lib/deploy-target.ts`, which `migrate-local.sh` repeats, and its simulated KV by the binding name. Give the dev config a KV id and the namespace moves to that id, away from where the skeleton smoke test looks.
- **pnpm 12 fails install on unapproved build scripts.** Add new ones to `allowBuilds` in `pnpm-workspace.yaml`.
- **Playwright** needs `pnpm exec playwright install chromium` once per machine.
- **The scratchpad directory is shared by every subagent of one session.** Two tickets writing `edit2.py` or `dev.log` there overwrite each other, and a script run by relative path then edits the wrong worktree's idea of a file. Keep scratch files in your own `node_modules/.tmp/`.
- **The worktree guard refuses a shell command it cannot read**: one that uses `$PWD` or another variable beside `git`, `pnpm` or `magick`, or a long heredoc. Write the path out, or put the steps in a script file under `node_modules/.tmp/` and run that.
- **Harmless dev noise**: a `NOSENTRY RPC connection broken` line from workerd at startup, sourcemap warnings, React's `eval()` notice.

## Agents that poll

- **A polling Agent extends `ViewerPolledAgent`** (`apps/web/agents/viewer-polled-agent.ts`) and writes `poll()`, `pollIntervalSeconds()` and `alertSource`. The base class owns the timer, the staleness check for first paint (`pollIfStale()`), the alert and the read-only rule. Its timer is a one-off `schedule()` that each poll sets again, never `scheduleEvery`, so the cadence can change between polls.
- **`pollIfStale()` waits for a poll that is under way** (#85). "Last polled" is written when a poll starts, not when it ends, so without the wait a caller arriving mid-poll is told the state is fresh and reads what the poll is about to replace: on a new Agent, nothing. Anything else that asks "is this fresh?" must ask about the poll in flight too.
- **A subclass that overrides `onConnect` or `onClose` must call `super`**, or polling never starts or never stops.
- **Connecting a page to the Scoreboard** is already done by the root route: see "Live scores on a page" below. `readScoreboard()` (`apps/web/lib/scoreboard.ts`) is first paint, read by the root's loader through `readShell`. Nothing a route's component imports may import `lib/scoreboard.ts`: it imports `cloudflare:workers`.
- **An alert is two log lines and nothing else** (#98). `EspnAlert` (`apps/web/agents/espn-alert.ts`) keeps the failure count and whether a problem is open in the Agent's storage, and calls `announce()` in the same file once when a problem starts (`console.error`, "Scoreboard: ESPN problem started: <reason>") and once when it clears (`console.log`, "... ESPN problem cleared"). `announce()` is the seam for a push channel: fill it in there and nothing else changes. `EspnAlert` logs an announcement that throws and carries on, so a channel that is down never fails a poll. ntfy was the channel until 2026-10-06, when Ryan had it removed; real push waits for a PWA.
- **The Worker has no secrets**, and `apps/web/env.d.ts`, which typed the one it had, is gone. `cloudflare.config.ts` has no way to declare a secret, so `cf workers types` leaves them out: a new one is typed by hand in an `env.d.ts` beside the config (`declare namespace Cloudflare { interface Env { NAME?: string } }`), given to tests through `bindings` in `apps/web/vitest.config.ts`, and uploaded with the deploy (`cf deploy --secrets-file`).

Never format a time anywhere else. A slate's date is the NHL's calendar day and is not converted.
- **A game going final runs the page's loaders again**: the provider calls `useRefreshOnInvalidation` with `invalidatedAt`, so the reading comes when the Scoreboard has forgotten the cached keys (see "Finished games"), not when the game's status changes, which is seconds earlier. Nothing else may call that hook: one refresh per page. The refresh does not replace the provider's games: the socket's state is newer than the server's.
- **"updated" is `heardAt`, not `updatedAt`** (#67). `updatedAt` in the state moves only when a poll finds a difference, because setting state sends all of it (about 4 KB for nine games) to every open page. A poll that finds nothing new stores the time (`heard-at` in the Agent's storage, which `getScoreboard()` returns as `heardAt` for first paint) and broadcasts `{ type: "scoreboard_heard", at }`, about 60 bytes. `useAgent` hands any message that is not the SDK's own to `onMessage`; the provider reads it with `heardAtFrom` and `heardAt` is the later of it and `state.updatedAt`. A new kind of small news for every page goes the same way: a typed message, not a field in the state.

## Finished games (#40)

- **A poll only notes work; a timer set for at once does it.** `ScoreboardAgent.onSlateTransitions` puts each final in the Agent's storage (`pending-final:<id>`) and `onSlateDateChange` notes where catch-up starts (`catch-up-from`); `recordFinals` and `catchUp` are the callbacks of one-off schedules set with a delay of 0. First paint therefore never waits on rosters or thirty scoreboards, and every good poll sets the timers again while anything is left, which is the retry.
- **Pages are told through `invalidatedAt` in `ScoreboardState`**, moved after the cached keys are forgotten: at a final, at the 5-minute second round and after a catch-up that recorded a game. The component holding the Scoreboard socket (`ScoreboardProvider`, since #67) calls `useRefreshOnInvalidation` (`apps/web/lib/use-refresh-on-invalidation.ts`), which calls `router.invalidate()` on each change. The field is optional in the schema because state stored before it existed lacks it.
- **`schedule(when, callback, payload, { idempotent: true })`** makes a one-off schedule that a second call with the same callback and payload finds instead of duplicating. It is what lets a final's work be repeated without a second pair of timers.
- **What a finished game needs done is in `apps/web/agents/final-game.ts`**: `saveFinal`, `invalidateForFinal`, `invalidateStandingsAndTeams`, `rereadArchivedPlays`. The Game Agent (#48) calls the same functions; `rereadArchivedPlays(db, gameId)` is the 24-hour re-read and what a Replay's first open wants after it has archived.
- **`startPrediction(game)` on `ScoreboardAgent` is where #52 starts a Prediction.** It is awaited inside the poll, and so inside first paint: start the model call from a schedule, as the finals are.
- **A final forgets the keys of about 50 players, three KV deletes each**, plus two ESPN requests for the rosters. A first visit after a full night of games does that for every game in one alarm. Not yet measured against the account's subrequest limit on Cloudflare.
- **Catch-up records only games ESPN calls final on the missed date.** It writes rows and forgets the standings and the teams; it sets no timers and forgets no players, as the spec has it.

## The Game Agent (#48)

- **Connecting a game page**, in two steps. The game's read (`findGame`, for the route's loader) calls `readGame(id)` (`apps/web/lib/game.ts`) for first paint: a `GameSnapshot`, `{ header, delayed, archived, plays, notFound }`, already a plain object. `notFound` is the not-found page. The page then calls `useGameStream(id, snapshot)` (`apps/web/lib/game/use-game-stream.ts`), which opens the socket and returns `{ header, delayed, archived, plays }`, current from then on: hand `header` and `plays` to `GameView`, and `delayed` is its `notice`. Nothing a route's component imports may import `lib/game.ts`: it imports `cloudflare:workers`; `lib/game-connection.ts` is the browser-safe part.
- **The plays are not in the Agent's state.** State is the header and two flags, sent whole on each change. Plays arrive as `GameStreamMessage`s (`packages/schemas/src/game-stream.ts`): `plays` (every play, on connect), `play-added`, `play-changed`, `play-removed`. `applyGameStreamMessage(plays, message)` is the reducer and `parseGameStreamMessage(event.data)` tells them from the Agents SDK's own messages on the same socket; the hook does both.
- **The socket is what makes the Agent poll.** Render the component that calls `useGameStream` only while the game is live or about to be; a page for a game three hours off that holds a socket costs a poll every 5 minutes. A final game's Agent never polls, socket or not.
- **`header.status === "final"` comes first, `archived` about 30 seconds later**, after the last poll and once the row and plays are in D1 (at once for a game that was already over when first read). A page that turns into the Replay (which reads D1) waits for `archived`. Once archived, the plays are gone from the Agent's storage, and its snapshot and its on-connect message read them from D1.
- **The Replay's first open of a game nobody watched** is `archiveGame(id)` (`lib/game.ts`), which calls the Agent's `ensureArchived()`: one read of ESPN, the row and plays into D1, the 24-hour re-read set on the Game Agent's own timer. It answers false for a game that is not final, or final with no plays from ESPN. The Scoreboard sets a re-read of its own at a final it sees, so a watched game is re-read twice; both are the same harmless replace.
- **An intermission is a live game whose last play is `period-end`**, not a clock at 0:00: the recorded summaries have no clock in the header, so the translation's "0:00" cannot be told from a real one. If #54 finds a live summary has a clock, nothing here needs it. `readSummary()` on the Agent is where the header would be given a different source.
- **A viewer who connects just after a first-paint read waits a full interval for the next poll**, because the staleness check counts from the last poll of any kind. In a test, `await agent.getGame()`, then `connect()`, then `later(10)`, not `later(0)`.
- **ESPN's answer in a test is the recorded shootout cut short** (`live(id, plays, edit)` in `game-agent.test.ts`): the raw response with its first N plays and `status.type` made in progress, through the real parser. Play 12 is the first goal, 97 the end of the 1st, 98 the start of the 2nd. The summary is asked for as `/summary?event=<id>` and the stub answers by event id, with a 404 for an id it was not given.
- **A restart test cannot use `ESPN_FIXTURES` here**, since the only recorded summaries are a final and a scheduled game. It spies on `readSummary` on the live instance until the restart (a spy that awaits no stubbed `fetch` does not stop the eviction) and the restart itself removes the spy.
- **`vi.spyOn(env.DB, "batch")` in a test reaches the Agent's D1**: `env` from `cloudflare:workers` is the same object the Agent holds. `replaceGamePlays` is the only `batch` in a final's write.
- **An idempotent `schedule` made from inside the callback of the same name and payload finds the timer that is running**, which is deleted when the callback returns. A callback that sets itself again does it without `idempotent`.
- **A timer's payload is part of what `idempotent` matches**, so the same callback with a different payload is a second timer. The Agent's `archive` timer is set only by the poll that first finds the game final, for that reason.
- **`/tmp` filling up also breaks the agent's own shell**: every command then reports `EDQUOT` and its output is lost, though the command ran. Send output to a file under `node_modules/.tmp` and read that. On 2026-10-06 the space was held by another project's session under `/tmp/claude-1000`, not by this repo.
- **No live summary was recorded**: no game was in progress on the afternoon this was built. `record-live.ts` is still the way to get one, and a test stepping through it would sit beside the cut-short ones.

## Predictions (#52)

- **Where it is.** `ScoreboardAgent.startPrediction(game)` only notes the game in the Agent's storage (`pending-prediction:<id>`); `makePredictions`, a one-off schedule set for at once, makes one model call per run and sets itself again while games are ready. One call per run because a model call takes 8 to 25 seconds and the Agent's timers run one after another: the Scoreboard's own poll waits behind whatever timer is running. The prompt, the inputs and the reading of an answer are in `apps/web/agents/prediction.ts`; the answer's schema is `predictionOutputSchema` in `packages/schemas`.
- **For the pages (#53).** `getPredictions(db, gameIds)` reads a slate's rows as a `Map` keyed by game id (a failed attempt is in it as its `failed` row; "pick pending" is a scheduled game with no entry). `pickOutcome(prediction, final)` in `packages/schemas` says `"right"`, `"wrong"` or null from anything with `home` and `away` carrying `id` and `score`; hand it a final game only. The Scoreboard moves `invalidatedAt` when a game's row is written, made or failed, so the loaders run again when a pick arrives. Prediction rows are not cached: a page's read takes them from D1.
- **The AI binding has nothing local behind it.** Under `pnpm dev` every call throws "Binding AI needs to be run remotely", so after three tries each scheduled game gets a `failed` row in the local D1 (in fixture mode only 401892449 gets as far as the model; the others have no recorded summary and fail on ESPN). - **Declaring the AI binding makes the Vite plugin open a session with the account as the dev server starts**, whatever the binding's `remote` says, which needs a login. `remoteBindings` in `apps/web/vite.config.ts` turns that off unless `AI_REMOTE=1`. `bindings.ai({ dev: { remote: false } })` is refused outright ("do not support local development"): leave the option out. Not run on a machine with no login; what was seen is that the dev server no longer prints "Establishing remote connection".
- **The two models answer in two shapes.** `gpt-oss-120b`: an OpenAI chat completion, the JSON as text in `choices[0].message.content`, its thinking in `message.reasoning`. The llama model: the same, plus `response` already parsed to an object. `readModelAnswer` reads both. `gpt-oss-120b` is not on Cloudflare's list of JSON-mode models and honours `response_format: { type: "json_schema" }` all the same. A model's request and response schema: `cf ai get-model-schema --model <id>`; one call from the shell: `cf ai run <model> --body @request.json`.
- **Reading the gateway's log**: `cf ai-gateway logs list --gateway-id yogan-hockey --order-by created_at --order-by-direction desc`, then `cf ai-gateway logs get-request <log-id> --gateway-id yogan-hockey` and `get-response` for the prompt and the answer. The list has tokens, cost, duration and the `gameId` metadata, and no bodies.
- **In a test the binding is replaced on the instance**: `runInDurableObject(agent, (instance) => Object.assign(instance, { env: { ...env, AI: stub } }))`. The pool has no AI binding, so in every other test file `env.AI` is undefined; their games are years before the faked clock, so no Prediction is started.
- **"Two or three sentences" is counted** by `countSentences` in `packages/schemas`, which knows that "3-1-0", ".926", "A. Stolarz" and "St. Louis" end nothing. It is what failed the llama answers; nothing `gpt-oss-120b` wrote failed it.

## Testing an Agent in the Workers pool

`apps/web/agents/scoreboard-agent.test.ts` is the worked example.

- **The Agent runs in the test's own isolate**, so `vi.stubGlobal("fetch", ...)`, `vi.stubEnv` and `vi.useFakeTimers` all reach it. Stubbing `fetch` puts recorded ESPN responses through the real parser, and a spy on `console.error` and `console.log` catches the alert's two log lines.
- **Fake only the clock**: `vi.useFakeTimers({ toFake: ["Date"], now })`. The Agents SDK decides what is due from `Date.now()`, so `vi.setSystemTime(...)` followed by `runDurableObjectAlarm(stub)` runs whatever schedule has come due. The alarm helper returns `false` when no alarm is set, which is how a test sees that polling has stopped. Leave `setTimeout` real, or `vi.waitFor` never ticks.
- **Many timer runs in one test go in one trip**: `runInDurableObject(stub, async (agent) => { while (...) await agent.alarm(); })` runs the SDK's alarm handler in place. A loop of `listSchedules` and `runDurableObjectAlarm` from the test is two trips into the Agent a run, and the two tests of the daily cap (forty runs each) took 2.5 seconds alone and passed Vitest's 5 on a busy machine. They take about 1.5 now and carry a 20 second timeout, since forty runs is what the cap is.
- **Set the faked clock ahead of the real one.** A schedule made by a clock that is behind is an alarm already due, and workerd fires it by itself.
- **A socket**: `routeAgentRequest(new Request("http://localhost/agents/<kebab-class>/<name>", { headers: { Upgrade: "websocket" } }), env)`, then `response.webSocket.accept()`. `onConnect` has run by the time it returns. On connect the SDK sends `cf_agent_identity`, `cf_agent_state` and `cf_agent_mcp_servers`; a write from the client is `{ type: "cf_agent_state", state }` and is answered with `cf_agent_state_error`.
- **`onClose` runs some time after `socket.close()`.** Wait for it: `vi.waitFor` on `runInDurableObject(stub, (agent) => [...agent.getConnections()].length)`.
- **A restart is `evictDurableObject(stub)`**: memory goes, storage, schedules and hibernated sockets stay. It needs a default export on the test entry, which is why the entry is `agents/test-worker.ts`. It hangs under a faked clock (switch to real timers around it) and it hangs for good once the Agent has awaited a `fetch` stubbed by the test, so a restart test uses `ESPN_FIXTURES=1` up to the restart.
- **`console.log` in a test does not reach the terminal.** `console.error` from the Agent does, so the failing-poll tests are noisy by design.
- **Biome reads a helper named `after` as a test hook** (`noDuplicateTestHooks`). Call it something else.
- **The tests of one file share Durable Object storage.** Give each test its own instance name.
- **`runDurableObjectAlarm` runs what is due and no more.** A schedule a callback sets for "now" waits for the next call, so after a poll that leaves work a test calls it once more (`visit()` in `scoreboard-finals.test.ts`). It returns true whenever any alarm was set, due or not.
- **A test's first call to an Agent starts it cold**, 2 to 5 seconds when other worktrees are running their suites, against Vitest's 5-second default. `lib/scoreboard.test.ts` timed out in the full suite for that reason and has a longer timeout; a test that fails only in the full run is likely this.
- **ESPN answering slowly** is a stub that awaits a promise the test resolves (`slow(id, answer)` in `game-agent.test.ts`): start one `agent.getGame()`, wait for `espnRequests` to reach 1, start another, and race it against a real `setTimeout` to see that it has not answered early.
- **A hook on the Agent can be spied on**: `runInDurableObject(stub, (instance) => vi.spyOn(instance, "method"))` reaches the live instance, since it is in the test's isolate.

## ESPN

- **Fixture mode is `ESPN_FIXTURES=1`**, read by `packages/espn` from `process.env` on every read. Under `pnpm dev` and `pnpm build` the Worker never sees the shell's environment, so `apps/web/vite.config.ts` compiles the variable in with `define`: set it when the dev server starts, and restart to change it. In Vitest, the Workers pool included, `vi.stubEnv("ESPN_FIXTURES", "1")` works. A build without it contains no recorded response; keep the test written out inside `read` in `client.ts`, because behind a function the bundler keeps the fixtures.
- **Fixture mode answers only what is recorded**: the current scoreboard (the slate of 2026-10-06, nine games), the scoreboard of 2026-10-03, standings, the team list, and Toronto (team 21) with its schedule. Since #35 also: two game summaries (401803652, a finished shootout from April 2026; 401892449, Nashville at Toronto while still scheduled), Auston Matthews (4024123) and the goalie Anthony Stolarz (3067313) each with profile, career and game log, and the search for `mar`. Anything else is an `EspnFetchError` naming the missing file. To add one, add a sample to `READS` in `packages/espn/check/samples.ts` (the one list the recorder and the daily live check share) and run `pnpm record:fixtures`.
- **No recorded slate has a live game yet.** Every game in `scoreboard.json` is scheduled and every game in `scoreboard-20261003.json` is final; nothing was on when they were recorded. The live and postponed cases in `scoreboard.test.ts` change the status of a recorded game. Run `pnpm record:fixtures` during an evening of games, then `pnpm test -u`, and tickets that need a mixed slate get a real one.
- **Recording rewrites `scoreboard.json` with whatever is on**, so the snapshots and the literals in the tests that name its games change with it. The dated slate and the rest move only as the season does (standings, records, the schedule's results).
- **ESPN answers an unknown team id with HTTP 400**, not 404. `EspnFetchError.notFound` covers both; use it for the not-found page.
- **A scoreboard asked for by date has no `day`**, and a range (`dates=20261005-20261006`) is a 400. Catch-up fetches one date at a time.
- **ESPN names the same thing differently by endpoint.** A side's overall record is type `total` on a slate still to be played and `ytd` on a finished one and on a schedule; a score is `"3"` on the scoreboard and `{ value: 3 }` on a schedule; the scoreboard sends one `logo`, everything else a list of `logos`; the season type is inside `season` on the scoreboard and beside it on a schedule. `espn-game.ts` and `espn-team.ts` absorb all of it into one `Game` and one `Team`.
- **Standings come from `standings?level=3`** (conference, then division). The default response has no divisions. `standingsView` in `packages/schemas` ranks the rows itself, so ESPN's order is not relied on.
- **Team stats come with team detail** (`teams/{id}?enable=roster,stats`): the overall record's stats carry goals, power play and penalty kill. The separate `teams/{id}/statistics` and `teams/{id}/roster` endpoints are not used.
- **The team schedule is asked for with `seasontype=2`**, the regular season; `1` is the preseason and `3` the playoffs, which nothing asks for yet. It is 1.1 MB for 84 games.
- **Playwright reuses a dev server that is already running** outside CI. One started without `ESPN_FIXTURES=1` gives the smoke tests live ESPN; stop it first.
- **`pkill -f "[v]ite dev"` does not match the dev server** `pnpm dev` leaves listening (its process is `node`), and it would match other worktrees' servers if it did. Stop yours by port: `kill $(ss -ltnp | grep ':5234' | grep -o 'pid=[0-9]*' | cut -d= -f2)`.
- **A search is recorded under its query** (`search-mar.json`), so in fixture mode any other query is an `EspnFetchError`. A smoke test of the players page searches for "mar".
- **A scheduled game's summary is recorded once.** `record-fixtures.ts` keeps `summary-401892449.json` if it exists, because recording it again after the game would replace the pre-game summary with a finished one. To get another scheduled game, add it to `RECORDED_ONCE` before it starts.
- **No in-progress summary is recorded yet.** The live probe's `probe-*.jsonl` held one `start` line each when #35 ran, and it logs diffs, not whole polls, so it could not have supplied one anyway. `node packages/espn/scripts/record-live.ts <eventId> [polls] [seconds]` writes whole polls of a live game to `fixtures/live/`; run it during a game and the Game Agent's diff tests have a real sequence. It was run against a finished game only.
- **The summary header's status has only `type` for a scheduled and a finished game**: no `period`, no `displayClock`. `translateGameSummary` reads them when they are there and otherwise takes the period from the last play (then the line score) and the clock as "0:00". Whether a live summary carries them is not yet seen; if it does not, the live clock has to come from the Scoreboard's `Game`.
- **A play's clock counts up** (a period starts at 0:00, overtime ends at 5:00), where the scoreboard's clock counts down.
- **A shootout is period 5 with every play at 0:00.** Its goals have `scoring: true` and do not move the running score, and the plays after overtime read one goal lower for the eventual loser than the plays before (3-3 at the end of overtime, then Dallas 3, Buffalo 2 through the shootout Dallas won, in 401803652). Take no score from plays.
- **A penalty is a play whose ESPN type has `penaltyMinutes`.** Its type abbreviation is the infraction's name with capitals and spaces ("Delaying Game-Puck over glass", "Fighting (maj)"), and its participants have no role. "End of Game" has no abbreviation at all, so its `type` is made from its wording: `end-of-game`.
- **In this fixture list order and `sequenceNumber` order agree.** The order the site keeps is the list's; a test swaps two plays to prove it.
- **The summary header's team has no `shortDisplayName` and no `logo`** (it has `name` and `logos`); the boxscore's team has both but no dark logo. The header's is the one translated.
- **ESPN's `atVs` is wrong for some road games** in the last five games and the game log ("vs" for a game played away). `homeTeamId` decides home or away.
- **A summary's last five games and goalies exist only before the game.** A finished game's `pregame` has standings, injuries, leaders and the season series, with `lastFive` and `goalies` empty. Early in a season the last five include preseason games.
- **Stat tables carry their own columns.** A skater's and a goalie's career and game log have different columns, and ESPN's labels mislead ("SOG" in a skater's career is shootout goals), so `PlayerCareer` and `PlayerGameLog` are `columns` plus rows of display strings. A season split between clubs has a row per club and then a totals row whose `team` is null.
- **A player yet to play in the NHL has a profile and turns up in search, and his stats and game log are 404s** (Sam O'Reilly, 5216901). `getPlayerCareer` and `getPlayerGameLog` answer an empty table for a 404; the profile is what says a player does not exist.
- **The game log is the latest season he played**, so before his first game of a new season it is all of last season (69 games for one player on 2026-10-06). `PlayerGameLog.season` says which; a "recent games" list takes the first few.
- **An unknown athlete or event id is a 404**, where an unknown team is a 400. `EspnFetchError.notFound` covers both. A search that finds nobody is a 200 with no items.
- **Athlete stats and game log answer on `site.web.api.espn.com`**; the profile and search on `site.api.espn.com`.
- **A name exported from two files of `packages/schemas` fails typecheck at the index** (`export *` twice). `SeasonRecord` is the picks' record; a team's is `TeamRecord`.

## The daily live ESPN check (#36)

- **Run it: `pnpm check:espn`.** It fetches live ESPN (15 or 16 requests, about five seconds), prints a line per endpoint, writes the run to `espn-check.json` (gitignored; `--summary <file>` names another) and exits 1 if anything failed. It is no part of `pnpm test` or CI: it needs the network, and ESPN being down must not fail a pull request.
- **Read a failure by its first word.** `PARSE <endpoint>` is the one that matters: ESPN answered and the answer is not the shape the site reads. The lines under it are Zod's, `path.into.the.response: what is wrong`, the path counted from the top of ESPN's JSON. Look at that path live (`curl -s '<the url printed>' | jq '.children[0].children[0] | keys'`, never the whole response), fix the schema and the translation in `packages/espn/src`, then `pnpm record:fixtures` and `pnpm test -u` so the fixtures hold the new shape. `FETCH <endpoint>` means ESPN or the network gave no answer after three tries (a 4xx is not retried: it is ESPN's answer; a 200 whose body is not JSON, such as a block page, counts as a fetch failure); one that passes the next day needs nothing done, and one that is a 404 every day means ESPN moved the endpoint.
- **`not checked:` lines are not failures.** The summaries of a live and of a scheduled game are chosen from today's slate when the check runs, so at 16:17 UTC there is usually no live game to check, and on a day without games neither. A live summary has still never been through the parsers (see the ESPN notes); a manual run during a game (`gh workflow run espn-check.yml`, or `pnpm check:espn` at home) is how to find out.
- **`packages/espn/check/samples.ts` is the one list of requests**, shared by the recorder and the check. `READS` is typed to have an entry for every builder in `endpoints`, each with its `translate*` function and at least one sample, so a read added to `endpoints.ts` fails typecheck until the check covers it. A read that built its URL without `endpoints` would escape, and `read()` in `client.ts` takes only an `Endpoint`.
- **The check calls the translations, not the `get*` reads**, so a career table or a game log that is a 404 fails the check, where the site reads it as an empty table.
- **The workflow is `.github/workflows/espn-check.yml`**, daily at 16:17 UTC and by hand (`gh workflow run espn-check.yml --ref <branch>`). It runs `pnpm check:espn` and then `packages/espn/scripts/report-check.ts`, which is where the issue is decided (`check/report.ts`, tested with `gh` stubbed). `--dry-run` on that script prints the `gh` commands without running them: `node packages/espn/scripts/report-check.ts --dry-run`.
- **One open issue at a time, found by its exact title**, "ESPN daily check is failing". A failure opens it (labelled `needs-triage`, making the label if the tracker has none) or comments on it; the first pass after a failure comments that it cleared, listing what that run did not check; later passes say nothing. Nothing closes it but a person, because a parse failure can depend on what was on that day. Rename the issue and the next failure opens a second one. Where things stand is read from hidden marks (`<!-- espn-check: failed -->`, `<!-- espn-check: cleared -->`) in what the check wrote.
- **The issue and the red run are the only notice** (#98): the check pushes nothing and reads no secret. If the tracker refuses the issue, the report step fails and the run is red for that too.
- **Runner verification (2026-10-11, #36).** The [manual main run](https://github.com/ryanyogan/yogan-hockey-2026/actions/runs/38153249723) passed all 15 fetched endpoints; the job took 19 seconds. A temporary branch adding required `divisionRank: z.number()` to `EspnDivision` [failed only standings](https://github.com/ryanyogan/yogan-hockey-2026/actions/runs/38153259132), and its successful report step opened [#113](https://github.com/ryanyogan/yogan-hockey-2026/issues/113) as `github-actions`, labelled `needs-triage`, with the endpoint, all four failing paths and the run link. This proves issue reporting with the runner's `GITHUB_TOKEN`; it does not independently prove label creation when the label is absent. No live game was available, so live-summary parsing remains outside these runs' evidence.
- **Repeating the failure drill.** Dispatch a healthy `main` run first. With no real ESPN failure issue open, push a temporary branch containing that one schema change and dispatch `gh workflow run espn-check.yml --ref <branch>`. Wait for its failed check and successful reporting step before dispatching `main` again. The [recovery run](https://github.com/ryanyogan/yogan-hockey-2026/actions/runs/38153323465) passed all 15 endpoints and automatically commented that #113 cleared; the deliberate test issue was then closed and the temporary local/remote branch deleted. Never merge or deploy the deliberately broken schema. The workflow serializes all branches through its shared `espn-check` concurrency group.
- **Node will not run a `.ts` file under `node_modules`** (`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`), so a scratch script in `node_modules/.tmp/` that imports the packages has to be `.mjs`.

## A page: `/nhl` is the pattern (#42)

- **The shape of a page with a query.** The route's `loaderDeps` hands the search whole to one pure function in `apps/web/lib` (`readNhlPage`) that returns what the page shows, every unknown value already replaced by its default. A second function (`nhlHref`) writes the URL back with the defaults left out, so each tab and view has one address. Both are tested in Vitest, as is anything else a page would otherwise work out inline (`apps/web/lib/standings-table.ts`). The title follows the tab the loader read (`titled` in the route's `head`).
- **Two rows of `UrlTabs`** share one `<div className="space-y-2">`, so the shell's 32px spacing applies to the block and not between the rows; the first row sits in a `SectionHeader` given `className="mb-0"`. Each `UrlTabs` needs its own `label`, which is also how a Playwright test tells them apart (`getByRole("navigation", { name: "NHL", exact: true })`).
- **A standings table anywhere is `StandingsLedger`**, given one `StandingsTable` from `standingsView`; the dashboard's can be the same component.
- **`className="w-full"` on the team's `LedgerColumn` gives that column the slack** in a standings table, which keeps the figures together and lined up from one stacked table to the next; `min-w-8` on the rank column does the same for the team names when a table reaches rank 10.
- **`cn` and the other class helpers are dependencies of `packages/ui` only.** A variant a page needs goes into the primitive (`LedgerCell tone="positive"`, `LedgerRow cutoff`), not into a `className` built in the app.
- **ESPN abbreviates Utah as "UTA" in the standings and "UTAH" in the team list.** Each is shown as ESPN sends it.
- **A test that opens several addresses cold gives each its own context** (`browser.newContext()`, as `e2e/nhl.spec.ts` does; `baseURL` still applies), which is a pasted link exactly and keeps to one hard navigation per page.
- **Reading again on a final needs nothing from the page.** `router.invalidate()` from whatever holds the Scoreboard socket runs its loader again. It shows the new standings only once the standings' key has been forgotten for that final.

## The game page's parts (#49)

- **The sample game page and its spec are gone** (#51): the Replay at `/nhl/games/401803652` is the page that draws the recorded shootout, and `e2e/replay.spec.ts` carries what the sample's test checked.
- **A game page renders one component**: `<GameView header plays tab pathname pick />` from `apps/web/components/game/game-view.tsx`. `header` is a `GameHeader`, `plays` every play so far in order, `tab` is the open tab, read from the address with `gameTabOfPath`, `pathname` the game's own path (the tabs are `UrlTabs` links back to it), `pick` whatever "the pick" tab shows. It keeps two things itself: the picked play and the key-plays toggle. Both survive a change of tab, because the tab is a navigation of the router's.
- **The Game Stream feeds it the Agent's state as it arrives; the Replay feeds it `plays.slice(0, playhead)`.** With no play picked the focus is the last play of `plays`, so a growing list follows the game and a playhead steps through it. The overlay's score, shots, period and clock come from `header` alone (never from plays), so a Replay showing the score at its playhead passes a header with them changed. `status` replaces the words over centre ice ("End of 2nd") and `notice` adds a warning under them ("Updates delayed"). `selectedId` and `onSelect` are for a page that must hold the pick itself; leave them out otherwise.
- **The parts are usable alone**, all props and no state: `GameRink` (`header`, `plays`, `drawn`, `focus`, `status`, `notice`), `Rink` (`plays`, `focus`), `PeriodTimeline` (`game`, `plays`, `ticks`, `focusId`, `selectedId`, `onSelect`), `PlaysList`, `ScoringSummary`, `KeyPlaysToggle`. Each takes every play as `plays` and the ones to show (key plays or all) separately, because placing a shootout tick and working out the ends both need the whole game.
- **ESPN's coordinates are fixed to the building**, so `rinkPoint` only turns y over; nothing is mirrored by period. Which end a team shoots at changes every period and the home team's first end differs by game, so `attackedEnd(plays, homeTeamId, teamId, period)` reads it from the shots and answers null before the first one. The evidence is in `docs/spec.md`, Unverified row 16.
- **The rink is drawn in feet** (`RINK` in `apps/web/lib/game/rink.ts`; viewBox 204 by 89, the Reference UI's), and everything laid over it is placed in `cqw`, fractions of the rink's width, inside an `@container`. Change the overlay by those fractions, not by viewport breakpoints. An end-zone circle spans 8.8% to 23.5% of the width and 8.4% to 42.1% of the height; the blue lines are at 37.75% and 62.25%; the centre circle spans 42.65% to 57.35%.
- **The timeline's widths are minutes**: 20 a period, 5 for overtime (20 in the playoffs, `seasonType` 3), and a shootout, which has no clock, the room of 8 with its plays spaced in order. `layoutTimeline(plays, game)` returns the periods and each play's place from 0 to 1.
- **The overlay's type is the Reference UI's, outside the ledger's sizes**: a 60px score, a 12px "LIVE", scaled down with the rink. Its corners are the ledger's: the reference rounds the caption, the timeline and the ticks, and the site rounds nothing.
- **`apps/web` has no `cn`**; it is a dependency of `packages/ui` only. The game components build class strings by hand.
- **A finished game's last play is "Game End"**, with no coordinate, so a Replay opened for browsing has a caption and no ringed dot until a play is picked.
- **Logic tests that need the recorded game** use `recordedShootout()` and `play({...})` from `apps/web/lib/game/test-plays.ts`.
- **Measuring the game page against the Reference UI**: the reference's rink is `svg[role=img]` at `/prototype/game?variant=C` on port 4517, the sample's is `[data-slot="rink"]`; every part of the sample has a `data-slot` (`rink-score`, `rink-status`, `rink-caption`, `rink-end`, `rink-mark`, `period-timeline`, `timeline-tick`, `play-row`). The reference page has no shell, so its rink is 1120px wide where the sample's is 1200 at 1440: compare fractions of the rink's width, not pixels.

## The game page: scheduled, live, final (#50)

- **The states** are `gamePhase(status)` in `apps/web/lib/game/page-state.ts`: `scheduled` (also a postponed game), `live`, `finished`. `GamePage` (`components/game/game-page.tsx`, given `key={id}`) draws whichever the newest status says: the server's snapshot until the socket is open, the stream's header after.
- **What opens the socket** is `streamStarts(snapshotStatus, scoreboardStatus)`: a snapshot that is live, or a scheduled one whose game the Scoreboard (`useScoreboard()`) reports live or final. `GamePage` keeps the answer in state once true, because the slate moves to another day under an open page and the loaders running again at a final hand it a new snapshot. `GameStream`, inside it, is the only caller of `useGameStream`. A game final when opened never gets a socket.
- **With the socket just opened the page still shows the matchup** until the Agent's header says live, so the rink never shows a scheduled header with a 0-0 score.
- **The words over centre ice are `streamReading`**: "End of 2nd" when the last play is `period-end`; the header's clock when it has one; when it is "0:00" (every recording), the Scoreboard's clock for the same game and period ("2nd 12:34", time left, as the ticker shows it); failing that the period alone. "Updates delayed" is its `notice`. #54 settles the clock against a real game: if a live summary carries a clock, the first rule already takes it.
- **`FinishedGame`** (`components/game/finished-game.tsx`) draws the Replay (see "The Replay (#51)"): props `gameId`, `header`, `plays`, `archived`, `notice`, `tab`, `pathname`, `pick`. A game that ends on an open page gets the stream's plays and `archived` turning true about 30 seconds later; a game opened after its final gets the snapshot's. Going from live to finished remounts `GameView`, so the picked play and the every-play choice start again; the Replay holds them itself anyway.
- **The pick is `GamePick`** (`components/game/game-pick.tsx`, drawn from a made Prediction). `GamePage` shows it as "The pick" section of the scheduled page and as the tab afterwards. See "The pick on the site (#53)".
- **The matchup facts are a cached read**, `cachedGamePregame(id)` in `lib/espn.ts` (15 minutes; `forgetGame` at a final), not part of the Agent's snapshot: only a scheduled page asks for it, and a failure draws nothing instead of failing the page. `GameMatchup` draws it; `MatchupRink` is the scheduled rink, sharing `GameRink`'s overlay places so the ice does not move at the switch.
- **An id that is not digits is not found without waking an Agent** (`findGame`, `lib/find-game.ts`), so a mistyped address makes no Durable Object.
- **Driving a game in Playwright**: `e2e/game-driver.ts`. `driveGame(page, id)` passes the Scoreboard's socket through (and pushes the slate with the game changed: `scoreboard({ status: "live", period, clock, scores })`) and answers the Game Agent's socket itself (`agent(state, plays)`, `message(...)`); `recordedGame(baseURL)` gets the shootout's plays from that game's real Agent over a Node `WebSocket` and renames its teams to the scheduled game's, since the only page that starts scheduled in fixture mode is 401892449. `node scripts/game-page-shots.ts` uses the same driver for the shots in `docs/design/game-page/`. Node runs the `.ts` itself, but not from under `node_modules`.
- **`getByText` on a status can wait forever**: the same words are in a hidden timeline label. Filter the `[data-slot="rink-status"]` locator by text instead.
- **A snapshot with no header and no `notFound` means ESPN did not answer** for a game the Agent has never seen (#85). `findGame` calls that `{ state: "unreadable" }` at once, which the page says in words ("This game could not be read just now") instead of answering 500; a read that throws is made once more, and a second throw is `unreadable` too. Nothing is remembered: `getGame()` on an Agent with no header asks ESPN on every call, whatever the polling interval. `findGame` returns a `GameLookup` (`found`, `missing`, `unreadable`), not a game or null.
- **Why first visits used to draw that message with ESPN answering** (#85): a poll stamps "last polled" as it starts, so a second `getGame()` arriving during an Agent's first poll found the Agent "fresh" and answered with the empty initial state. Two reads of one game that overlap are enough, and two requests for one game make them. `pollIfStale()` now waits for a poll under way. The earlier guess, a cold start, was this.

## The Replay (#51)

- **The rules are `replayReducer` in `apps/web/lib/game/replay.ts`**, tested in `replay.test.ts`. The playhead is an index into every play of the game, or null for the whole game laid out, which is how a Replay opens and where playing ends. It is never an index into the Key plays, so the key-plays toggle cannot move it; the toggle decides only what a step lands on (the Key plays, or every play once every play is listed). The game's last play, "Game End", is the whole game: stepping or clicking onto it is the end.
- **Play from the whole game starts again at the first play.** A step is 1.2 seconds at 1x (`stepMilliseconds`), 2x and 4x divide it; the game's real gaps are not followed.
- **`Replay` (`components/game/replay.tsx`) gives `GameView` the game at the playhead**: `plays` up to it, `upcoming` for the rest (faint ticks that can be clicked; they also keep the timeline's layout and the rink's ends where the whole game puts them), `headerAt` for the score and shots, `statusAt` for the words over centre ice, and the controls as `transport`, which takes the place of the timeline's hint. `GameView`'s `everyPlay` and `selectedId` are controlled by it.
- **A shootout play's running score is not the game's**: in the recording every shootout play says 3-2 through a 3-3 shootout. `headerAt` takes the score from the last play before the shootout, and the final from the header alone (only the header gives the winner its extra goal).
- **ESPN has no running shots**, so `headerAt` counts shots on goal and goals up to the playhead, shootout left out. For the recording that makes 53 by the end where the header says 28 and 24, so the count can be one off just before the end; the whole game shows the header's own.
- **Where the plays come from** is `lib/replay.ts`. `replayGame(found)` in the game's read (`lib/game-page.ts`): a snapshot the Agent calls archived already carries D1's plays (the Agent reads them with `getGameWithPlays`), so nothing more is read; a final one that is not archived gets `replayPlays(id)`, which reads D1, and only if the plays are missing calls `archiveGame(id)` and reads D1 again. The second open is one D1 read and no ESPN.
- **The header is still the Game Agent's**, not D1's: a `games` row has no shots, names or "Final/SO". For a final game the Agent answers from its stored state without asking ESPN.
- **A page that saw the game end** shows the stream's plays for browsing with the transport's place held (`ReplayPending`), and `FinishedGame` calls the server function `readReplayPlays` (`src/functions/game.ts`): at once when `archived` turns true, otherwise every 10 seconds for two minutes. It becomes the Replay when plays come back. This path has no browser test: the driven game in `e2e/game-driver.ts` is the scheduled fixture, which the real Agent will never archive.
- **`ensureArchived()` answers false while the last poll is still to come** (an `archive` timer with `lastPoll: true`). Without that, any open of the page in the half minute after a final, including the reading again that the Scoreboard causes on the page that watched it, wrote the game before ESPN's closing plays.
- **A timeline tick and its play's row have the same accessible name** ("2nd 4:24 Esa Lindell Goal ..."), so `getByRole("button", { name })` matches two. Find a tick as `[data-slot="timeline-tick"][aria-label^="2nd 4:24 "]`. Ticks for plays not yet reached have `data-upcoming`.
- **The whole game has one more tick than Key plays** (75 for the recording's 74): the play in focus is always drawn, and "Game End" is not a Key play.
- **`node scripts/replay-shots.ts [baseURL] [outDir]`** takes the shots in `docs/design/replay/` (opened, playing, end; light and dark; 1440 and 390) against a fixture-mode dev server.
- **This machine has no `lsof`.** A script that stops a server with it stops nothing and says nothing; Playwright then reuses the stale server, and with `.cloudflare/state` deleted under it every spec fails. Use the `ss -ltnp` line in the Playwright notes.
- **The recorded scheduled game lists Sergei Bobrovsky under Toronto** because ESPN's `goalies.homeTeam` (`teamId` 21) does. The translation was not at fault; since #51 it gives each team the list carrying its `teamId` rather than trusting the `homeTeam`/`awayTeam` key.

## A page with an id: the team page (#43)

- **`findTeam` (`apps/web/lib/find-team.ts`) is the pattern for a page with an id**: null for an id that cannot be one (`packages/espn` throws a `RangeError` for anything but digits, before asking ESPN) and for ESPN's "no such thing", an error for everything else.
- **Fixture mode cannot show an unknown team**: every team but Toronto is a missing fixture, which is an error and not a 404: the error page, with a 503 (see "Not found and failure"). The smoke test's not-found case is an id that is not digits; the 400 from ESPN is covered in `find-team.test.ts`.
- **A time in the visitor's zone is `LocalTime`**: see "Live scores on a page". A screenshot or a Playwright test sees the browser's zone: set `timezoneId` on the context (`test.use({ timezoneId })` in `e2e/live.spec.ts`) and assert that zone's time, which has no "ET" after it.
- **The team page's cached `nextGame` can be an hour old**, so it may name a game that has started or finished. `nextGame()` and `liveGame()` in `apps/web/lib/team-schedule.ts` ask the Scoreboard, and `TeamNow` (on `useScoreboard()`) draws the banner or the Next Game card from them, so both change without a refresh. Anything that shows "next" or "live" for one team should use them.
- **`GameLedger` needs about 670px from `sm` up** (its columns are fixed). In half of a two-column grid at 1440 it loses the home score off the right edge, so the banner spans both columns (`xl:col-span-2`).
- **Links to a game and to a player are `gameHref` (`lib/scoreboard-view.ts`, which takes a `Game` too) and `playerHref` (`lib/roster.ts`)**, beside `teamHref`.
- **One row of figures under a header** (the team's record, its season stats): give the last column `w-full` so the figures stay together at the left, as the standings give it to the team. A ledger of names across the whole 1200px page is too wide to read across; the roster keeps to the first column of `grid gap-8 xl:grid-cols-2`.
- **A one-row ledger must not wrap on a phone.** Three columns of a game (day, opponent, time) leave about 120px at 390: the arena is hidden below `sm` (`max-sm:hidden` on the column and the cell).
- **A heart in a row that links** (#45): the row's link covers the row, so a button in a later cell needs `relative` to be clickable. `RosterLedger` takes it as `action`, `TeamHeader` as `action` too.
- **Measure page weight on a build, not the dev server**: `pnpm build` and `pnpm exec vite preview --port <PORT> --strictPort` in `apps/web`; build with `ESPN_FIXTURES=1` to preview fixture mode.
- **No recorded slate has a live game**, so the "Playing now" banner cannot be reached in fixture mode. The shots in `docs/design/team/live-banner-*` were taken with one recorded game made live inside `TeamNow` for the shot and changed back. `StaticScoreboard` around a component is the way to do it in a sample page.
- **Chromium started by a script needs `TMPDIR` too.** Without it `page.evaluate` fails with "Target crashed" on the first page.
- **The banner can be reached without touching `TeamNow`** (#83): stand between the page and the Scoreboard's socket with `page.routeWebSocket` and push the recorded slate with 401892449 made live, as `e2e/team.spec.ts` does. The `live-banner-*` shots have been taken that way since, by a throwaway Playwright script.
- **The team page's picks** (#83, #188) come with the team's read (`readSlatePicks()` in `readTeam`) and reach `TeamNow` as a prop: the banner's row gets them as `/nhl/live`'s rows do, and the Next Game card asks `nextGamePick` (`lib/team-schedule.ts`), which gives a line only for a game on the Scoreboard's slate now. On the card the pick leads the "where" cell, as in a game row's note; on a phone, where that column is hidden, it stands beside the time on the same line, so the row keeps its height (32.5px). Its gap is `ml-2` because the longest row ("Wed Oct 28", "10:00 PM", "pick pending") then ends 2px inside the 358px ledger at 390.
- **The team page's shots are taken with picks seeded** (`/skeleton/picks`, or after a Playwright run), each at the page's own height: `node scripts/screenshot.mjs <url> <out> <width> <scheme> <height>`, the height from `--eval=document.documentElement.scrollHeight`.

## Favorites (#45)

- **Everything reads favorites through `useFavorites(kind)`** (`apps/web/lib/use-favorites.ts`, `kind` is `"player"` or `"team"`): `{ ids, ready, has, toggle }`. The pure half is `apps/web/lib/favorites.ts`: `readFavoriteIds`, `toggleFavorite`, `favoritesFirst(games, teamIds)`, `isFavoriteGame`. `localStorage` holds `favorite_players` and `favorite_teams`, each a JSON array of id strings, oldest first, at most 24. The players' key and shape are the Parity Reference's.
- **`ids` is empty on the server and on the browser's first render**, and `ready` is false until hydration is over. Draw a heart or a marker from `has()` and it fills in by itself; a list must wait for `ready` before it says "none yet". `use-local-storage-state` 20 works with no hydration warning, keeps every hook on the page and every tab in step, and answers the default for JSON it cannot parse; JSON of the wrong shape is `readFavoriteIds`' job.
- **A heart is `<FavoriteHeart kind id name />`** (`components/favorites/favorite-heart.tsx`): the team page passes `action={(player) => <FavoriteHeart ... />}` to `RosterLedger`. Its button is `HeartButton` in `packages/ui`: one em square, drawn, with its reach in `::after` (how far it reaches is under "The primitives in agate").

The dashboard is `useFavoritePlayers(4)` and a `note` that compares `player.team?.id` with `useScoreboard().games`. The server function underneath is `resolveFavoritePlayers` (`src/functions/favorites.ts`); it goes through `loadPlayer`, so a player who is not ESPN's resolves once `loadPlayer` knows him.
- **Favorite teams' games**: `favoritesFirst` keeps the order inside each group, so sort first and call it last. `GameLedger` takes `favoriteTeamIds` and marks the row; it does not reorder.
- **A flex header that wraps sends its `action` to a line of its own on a phone.** `TeamHeader` and `PlayerHeader` do not wrap for that reason: the heading wraps inside itself and the heart stays on the first line.
- **Shots with favorites**: `node scripts/screenshot.mjs <url> <out> <width> <scheme> <height> '--store=favorite_players=["4024123"]' '--store=favorite_teams=["21"]'`; `--eval=<expression>` prints a measurement from the same page.
- **The Bash tool refuses compound commands that mix variables with `git`, `pnpm`, `sed` or `magick`** in a worktree-isolated subagent. Put the sequence in a script under `node_modules/.tmp` and run that; run each `git` command alone.
- **Not tried**: two tabs at once (the package's `storage` listener is relied on), and a private window where storage is refused.

## The dashboard (#47; Home was redrawn in #171)

- **The same pick on any other game row** is `GameLedger`'s `pick={(game) => ...}` (`/nhl/live` passes it too). It is drawn in the note column after the favorite marker (`[data-slot="game-pick"]`) and, on a phone, takes the venue's place in the small line under the status, where there is room for one or the other.
- **`GameLedger fitted`** is for a ledger that stands alone: from `sm` the columns size to their contents and the note has the rest, cut short with `max-w-0 truncate` (a cell that wide never widens its column, even in an auto-layout table); from `xl` the columns are the percentages the Reference UI's table measures at 1440. Stacked ledgers (`/nhl/live`) keep the fixed widths so they line up.
- **The Scoreboard's games carry `broadcasts` since #47**, optional in the schema because state stored before then has none until the next poll that finds a difference.
- **A one-column grid needs `grid-cols-1`**: a bare `grid` sizes its implicit column to the widest child, so a ledger with a `whitespace-nowrap` line made every block wider than a phone. With `grid-cols-1` the column is `minmax(0, 1fr)` and a wide ledger scrolls inside its own box.

- **A compact `PlayerLedger` names the team in full** to a screen reader and on hover: an `<abbr title>` holding the abbreviation (`aria-hidden`) and the name (`sr-only`). Playwright's `toHaveText` sees both.
- **A new spec file that sorts first meets a cold Scoreboard.** `e2e/dashboard.spec.ts` is the first to run; it passes from cold because the root loader's read asks the Scoreboard, which polls before answering. Deleting `apps/web/.cloudflare/state` under a running dev server leaves a Scoreboard that never answers ("Today's games could not be read"): stop the server first.

## Team marks (#97)

- **A team's mark is `<TeamMark teamId={id} />`** (`apps/web/components/team-mark.tsx`). It lives in the app, not `packages/ui`, because it knows the app's static files. Every shape that names a team carries ESPN's team id (standings rows, schedule opponents, a player's team, the Scoreboard's sides), and the id alone finds the mark: no team list is read. The `logo` and `logoDark` URLs in the schemas are drawn nowhere.
- **The slot convention**: the mark goes immediately before the abbreviation or name, inside the row's link where there is one, and the slot is the 14px box plus 6px (`mr-1.5`; pass `className` to change the gap). The box is kept when a team has no mark (an id not in the list, a player with no club), so a column's text starts at one x. `size="row"` is 14px beside 13px type, lowered 2px (`align-[-2px]`) so the line box does not grow: rows stayed 32.5px, 28.5px compact, the header 23.5px. `size="line"` is 1.2em for type that is not 13px (over the ice); `size="header"` is 20px with `-my-1`.
- **A cell that gets a mark needs `whitespace-nowrap`**, or a narrow column breaks between the mark and the text and the row grows to 52px.
- **`hang` is for a table whose columns are sized by their contents** (the dashboard's compact standings): a mark that took room moved every figure by 10 to 26px, so there it is absolutely placed in the 20px left of the abbreviation, inside the rank column's spare room, and takes none. It needs that room to exist: in a game row the column before a team is a right-aligned score.
- **Where a mark did not fit**: the team page's title line (with a mark "Toronto Maple Leafs Toronto · Eastern Conference · Atlantic Division" no longer fits half of a wide page, and the header went from 19.5px to 39px), so the team's mark is at the end of its record row and hidden below `sm`, where "6th in Atlantic Division" has 20px to spare; the Next Game card on a phone (its longest row ends 2px inside 358px); the game page's matchup ledgers (the goalie ledger is exactly 358px wide at 390, and a mark made the page scroll sideways by 11px).
- **Light and dark**: 10 of the 32 clubs have a dark logo that differs. Those have two `<img>`s and `dark:hidden` / `hidden dark:block` picks one; both are `loading="lazy"`, because Chromium never requests a lazy image that is `display: none`, so the other theme's file is not fetched. `eager` therefore holds only for a club with one logo.
- **The images are ours**: `pnpm team-marks` (`scripts/team-marks.ts`, needs the network) reads ESPN's team list, downloads each 500px logo (about 70 KB), trims its transparent margin, and writes WebP at 28, 42 and 84px to `apps/web/public/team-marks/<id>[-dark]-<px>.<hash>.webp` (126 files, 245 KB in all) and the list `apps/web/lib/team-marks.generated.ts`. Run it when a club changes its logo or the league gains a team, and commit the result; `lib/team-mark.test.ts` fails if the list and the files disagree. The hash is of the team's files, so `public/_headers` serves `/team-marks/*` as `immutable` for a year. A row's mark is the 28px file (2x) or the 42px one (3x): all 32 are 29.6 KB at 2x, 49.4 KB at 3x.
- **A file in `apps/web/public/` is answered by the platform before the Worker runs**, with the headers `public/_headers` sets. Checked on a build: a mark answers `cache-control: public, max-age=31536000, immutable`. A path with no such file reaches the Worker.
- **The sample slate's teams have ESPN's ids** (`ESPN_IDS` in `sample-slate.ts`), so `/skeleton/live` and `/skeleton/dashboard` show marks.
- **Shots**: `docs/design/team-marks/` is the tuned ledger's, a mark on every row. The script that retook it was deleted with #174: Agate has no mark on a row, and two of its routes are gone.

## A dropped socket, and shooting the error page (#84)

- **Screenshots of the error page come from a build**: `ESPN_FIXTURES=1 pnpm build`, `pnpm exec vite preview --port <PORT> --strictPort` in `apps/web`, `node scripts/error-shots.ts <url>`. The page itself and its statuses are under "Not found and failure".
- **`vite preview` had a D1 with no tables** ("no such table: predictions" in its log; why was not looked into), so the picks fail quietly and a finished game's Agent cannot archive: `recordedGame()` of the game driver times out against it. Anything that drives a game runs against the dev server (`node scripts/error-shots.ts <url> <dir> game`).
- **A dropped socket is told from a blip by `watchForDrop`** (`lib/connection-drop.ts`, tested with fake timers; `useDropWatch` is the hook): hand its `opened` and `closed` to `useAgent` as `onOpen` and `onClose`, and `dropped` is true once the socket has been down four seconds, counted from the first close, since every failed attempt to reconnect closes again. The Scoreboard's is `useScoreboardDropped()` from the provider, drawn by `ScoreboardNotice` under the ticker ("Reconnecting to live scores"); the Game Agent's is `reconnecting` from `useGameStream`, which `streamReading` turns into the rink's notice ("Reconnecting", in place of "Updates delayed", and nothing once the game is final). A socket that never opened counts as dropped too.
- **A Playwright script can drop a socket**: close the routed `WebSocketRoute` and close each new one in the handler until told otherwise (`scoreboardSwitch` in `scripts/error-shots.ts`; `agentDown(true)` on the game driver). PartySocket comes back about three seconds after the route lets it.
