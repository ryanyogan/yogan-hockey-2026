# Build notes

What earlier tickets learned that the code does not show. Read before building; add a line when you learn something the next subagent would otherwise rediscover. Keep each note to what cannot be found by reading the code.

## Running things

- **Ports.** The dev server is pinned to `PORT` (default 5173) with `strictPort`. Parallel worktrees each use their own `PORT`; the orchestrator assigns it. vinext refuses a second dev server in the same directory, so stop strays before Playwright.
- **Set `TMPDIR` to a directory on disk before running anything**: `export TMPDIR="$PWD/node_modules/.tmp" && mkdir -p "$TMPDIR"`. `/tmp` on this machine is a small tmpfs with a per-user quota, shared by every worktree, and the dev server, Vitest and Playwright fill it. The symptoms look like code faults and are not: `Unknown system error -122` in Vitest, `net::ERR_INSUFFICIENT_RESOURCES` or `Failed to fetch dynamically imported module` in Playwright.
- **Killing strays.** Stop your own dev server by its port: `fuser -k -n tcp <PORT>` (this machine has no `lsof`, and a script that kills by `lsof` output kills nothing and says nothing). `pkill -f` is not scoped to your worktree, so it can kill another subagent's server, and a pattern that appears in your own command line kills your shell.
- **`cf d1 migrations apply --local` fails to exit about half the time** (cf 1.0.0-beta.12). `apps/web/scripts/migrate-local.sh` retries it; call that, never the bare command, in anything Playwright or CI waits on.
- **`cf d1 migrations apply` accepts only a database id**, and `bindings.kv()` only an id. The real ids live in `apps/web/cloudflare.resources.json`. Local dev uses neither: it keys its simulated D1 by `LOCAL_D1_ID` in `apps/web/lib/deploy-target.ts`, which `migrate-local.sh` repeats, and its simulated KV by the binding name. Give the dev config a KV id and the namespace moves to that id, away from where the skeleton smoke test looks.
- **pnpm 12 fails install on unapproved build scripts.** Add new ones to `allowBuilds` in `pnpm-workspace.yaml`.
- **Playwright** needs `pnpm exec playwright install chromium` once per machine.
- **The scratchpad directory is shared by every subagent of one session.** Two tickets writing `edit2.py` or `dev.log` there overwrite each other, and a script run by relative path then edits the wrong worktree's idea of a file. Keep scratch files in your own `node_modules/.tmp/`.
- **The worktree guard refuses a shell command it cannot read**: one that uses `$PWD` or another variable beside `git`, `pnpm` or `magick`, or a long heredoc. Write the path out, or put the steps in a script file under `node_modules/.tmp/` and run that.
- **Harmless dev noise**: a `NOSENTRY RPC connection broken` line from workerd at startup, sourcemap warnings, React's `eval()` notice.

## CI and deploy

- **What runs.** `CI` (`.github/workflows/ci.yml`) on every pull request, two jobs side by side: "Biome, typecheck, Vitest, build" and "Playwright smoke tests". `Preview` on every pull request and `Deploy` on a push to `main`, each a gate job and a deploy job. `Deploy` runs the CI jobs again on the merged code and deploys only if they pass.
- **`ESPN check` (`.github/workflows/espn-check.yml`) is not CI**: it runs daily and by hand, never on a pull request. See "The daily live ESPN check" below.
- **Nothing in CI needs a Cloudflare login.** `cf workers types`, `cf deploy --dry-run` (the build step: a production build plus the checks cf makes before uploading), the local migrations and `pnpm dev` all ran in a clean `ubuntu:24.04` container with no credentials. Do not add a secret to make a check pass.
- **Reading a failed run.** `gh pr checks <n>`, then `gh run view <run-id> --log-failed | tail -60`: never the whole log. A failed Playwright run uploads `playwright-traces`: `gh run download <run-id> -n playwright-traces`, then `pnpm exec playwright show-trace <trace.zip>`. If `--log-failed` says "log not found", the job never started: read its annotation with `gh api repos/ryanyogan/yogan-hockey-2026/check-runs/<job-id>/annotations` (on #33's own pull request it was the account's Actions billing).
- **How long it takes.** In a clean container, cold, after #34: tools 10s, install 22s, Biome under 1s, typecheck 6s, Vitest 10s, build 11s, Chromium with its system packages 41s, Playwright 29s (most of it `pnpm dev` starting). Setting up a runner costs more than all four fast checks together, which is why they share a job. Not yet timed on a GitHub runner; add the numbers here when a run has finished.
- **Caches** are the pnpm store (keyed by the lockfile) and Playwright's Chromium headless shell (keyed by the Playwright version). A cache saved on a pull request is readable only by that pull request; `Deploy` running the CI jobs on `main` is what warms them for everyone.
- **What turns the deploys on.** Both gates (`scripts/deploy-gate.sh`) need the `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` secrets, which `scripts/account-setup.sh` sets, and the target's KV and D1 ids in `apps/web/cloudflare.resources.json`. The ids are in; the secrets are the switch for production. Without them the deploy job shows as skipped and the gate leaves a notice on the run saying what is missing. Previews stay off whatever is set (next note).
- **Previews are switched off** at the top of `scripts/deploy-gate.sh`; no preview has ever been deployed. What is known, from cf 1.0.0-beta.12's own code: `cf previews deploy` binds KV and D1 exactly as the config names them, which is why `deployTarget` (`apps/web/lib/deploy-target.ts`) picks the shared preview pair when `isPreview` is set, and cf has no per-preview stores. `bindings.durableObject` requires `worker`, cf sends it as `script_name` with a preview too, and cf counts only a binding without one as the preview's own, so a preview may reach production's Agents, which write production's stores. A preview is uploaded with `preview_urls` forced on, which is a public `workers.dev` address, and cf refuses a preview whose config has `domains`. There is no `--dry-run` for a preview and no command to delete one. Turn previews on only after one has been shown to write the preview D1 and not production's.
- **A `run:` step that pipes needs `shell: bash` named**, or GitHub runs it without `pipefail` and a failed command before the pipe passes. A failure inside `echo "$(...)"` passes either way: assign it to a variable first.
- **Runners are pinned to `ubuntu-24.04`.** `ubuntu-latest` moves to Ubuntu 26 from 2026-10-19; move on purpose, checking Playwright's Chromium still starts.

## vinext and the Agents

- **Typed Agent namespaces come from `exports`**: `getAgentByName(exports.SomeAgent, name)` with `exports` from `cloudflare:workers`. `env.SomeAgent` types as `DurableObjectNamespace<undefined>`.
- **`revalidateTag` outside a page request** returns `undefined` and leaves the write floating. Use `apps/web/lib/invalidate-tag.ts`, which makes it awaitable through an undocumented vinext import.
- **A Server Action that changes data through an Agent** must call `refresh()` from `next/cache`, or the page does not re-render.
- **shadcn Base UI components arrive without `"use client"`.** Rendered by a server component they fail with `createContext is not a function`. Add the line to each new component a server component renders.
- **The Workers-runtime tests do not read `cloudflare.config.ts`.** `apps/web/vitest.config.ts` repeats the bindings: each new Agent or binding goes in both (except `AI`, which the pool cannot provide without a login; see "Predictions"). Its entry is `apps/web/agents/index.ts`, it aliases `next/cache` to `vinext/shims/cache`, and it runs on compatibility date 2026-08-22, the newest the pool's workerd accepts.
- **vitest is held at 4.x** because `@cloudflare/vitest-pool-workers` 0.22 requires it.

## Agents that poll

- **A polling Agent extends `ViewerPolledAgent`** (`apps/web/agents/viewer-polled-agent.ts`) and writes `poll()`, `pollIntervalSeconds()` and `alertSource`. The base class owns the timer, the staleness check for first paint (`pollIfStale()`), the alert and the read-only rule. Its timer is a one-off `schedule()` that each poll sets again, never `scheduleEvery`, so the cadence can change between polls.
- **A subclass that overrides `onConnect` or `onClose` must call `super`**, or polling never starts or never stops.
- **Connecting a page to the Scoreboard** is already done by the root layout: see "Live scores on a page" below. `readScoreboard()` (`apps/web/lib/scoreboard.ts`) is the layout's first paint; a page does not call it again. A client component must not import `lib/scoreboard.ts`: it imports `cloudflare:workers`.
- **Worker secrets are typed by hand** in `apps/web/env.d.ts`; `cloudflare.config.ts` has no way to declare one. `NTFY_TOPIC` is the only one. Tests get it from `bindings` in `apps/web/vitest.config.ts`.

## Live scores on a page (#41)

- **One socket per page, in the root layout.** `ScoreboardProvider` (`apps/web/components/scoreboard/scoreboard-provider.tsx`) wraps the shell with the layout's `readScoreboard()` for first paint and holds the only `useAgent` to the Scoreboard. Never call `useAgent` for the Scoreboard anywhere else.
- **A page shows today's games with `useScoreboard()`** from the same file, in a client component: it returns the Scoreboard's state plus `heardAt` (`ScoreboardReading`: `{ date, games, updatedAt, invalidatedAt, heardAt }`) and re-renders on every push. Each game carries its `venue` and each side its `record`; a side has no `shortName` any more, since nothing drew it (#67). A server component that needs scores renders a small client component that calls the hook; it does not read the Scoreboard itself. To find one game or one team's game: `useScoreboard().games.find(...)`.
- **How a game reads is in `apps/web/lib/scoreboard-view.ts`** (client-safe, tested): `gameStatusLine(game)` ("2nd 12:34", "end 2nd", "SO", "final/OT", "postponed", and null for a game still to be played, whose status is its start time), `slateSections(games)` (live, upcoming, final, postponed, each by start time), `tickerGames`, `gameHref`, `hasScore`. Draw a status with `<GameStatus game={game} />` (`components/scoreboard/game-status.tsx`), which puts the start time in for a scheduled game. `GameLedger` (`components/scoreboard/game-ledger.tsx`) draws games as the Reference UI's tonight rows; its last column is the note (favorite marker, the pick, then `gameWhere(game)`: the venue and who shows the game).
- **Every time is the visitor's own, through `LocalTime`** (`apps/web/components/local-time.tsx`, `<LocalTime at={iso} show="day" | "time" | "clock" />`): a game's start in the ticker, on `/nhl/live` and on the team page, and the "updated" stamp. The server cannot know the visitor's zone, so it writes Eastern time marked "ET" and the browser replaces it as the page hydrates. All formatting is in `apps/web/lib/game-time.ts` (`gameDay`, `gameTime`, `clockTime`, `slateDay`), assembled from `formatToParts` because the space before "PM" differs between workerd and Chrome. Never format a time anywhere else. A slate's date is the NHL's calendar day and is not converted.
- **A game going final re-renders the page's server components**: the provider calls `useRefreshOnInvalidation(state.invalidatedAt)`, so the refresh comes when the Scoreboard has written the tags (see "Finished games"), not when the game's status changes, which is seconds earlier. Nothing else may call that hook: one refresh per page. The refresh does not replace the provider's games: the socket's state is newer than the server's.
- **"updated" is `heardAt`, not `updatedAt`** (#67). `updatedAt` in the state moves only when a poll finds a difference, because setting state sends all of it (about 4 KB for nine games) to every open page. A poll that finds nothing new stores the time (`heard-at` in the Agent's storage, which `getScoreboard()` returns as `heardAt` for first paint) and broadcasts `{ type: "scoreboard_heard", at }`, about 60 bytes. `useAgent` hands any message that is not the SDK's own to `onMessage`; the provider reads it with `heardAtFrom` and `heardAt` is the later of it and `state.updatedAt`. A new kind of small news for every page goes the same way: a typed message, not a field in the state.
- **The ticker scrolls sideways under a vertical wheel** (`wheelScrollLeft` in `scoreboard-view.ts`, wired by a ref callback in `score-ticker.tsx`). The listener is added by hand because React's `onWheel` is passive and cannot stop the page scrolling too. At either end the wheel scrolls the page again.
- **A game row on a phone has two lines**: an abbreviation with its record does not fit twice beside a status in 358px (a late-season "45-25-12" is 8 characters), so below `sm` the record drops under its team and the venue sits under the status as `<LedgerDetail fine>`: 10px, wrapping, always the room of two lines so every row is one height. From `sm` up the row is the Reference UI's one line, the venue in its "note" column. `/skeleton/live` has the longest record and the longest venue name to look at.
- **`sr-only` text inside a box that scrolls sideways widens the whole page** unless the scrolling box is `relative`: the hidden text is absolutely positioned and escapes the overflow. The ticker's list and `Ledger` are both positioned for this reason.
- **A mixed slate without ESPN**: `/skeleton/live` draws the ticker and the `/nhl/live` sections from `apps/web/app/skeleton/live/sample-slate.ts` (play, an intermission, overtime, a shootout, three kinds of final, a postponement) through `StaticScoreboard`, a provider with no socket; `?slate=empty` is a day with no games. The shell's own ticker above it still shows the real slate.
- **A Playwright test can play the Scoreboard**: `page.routeWebSocket(/\/agents\/scoreboard-agent\/main/, ...)` with `connectToServer()`, forwarding the Agent's messages and sending `{ type: "cf_agent_state", state }` of its own. `e2e/live.spec.ts` uses it to make a recorded game go live and then final, to move `invalidatedAt` (which is what makes the page ask the server again) and to send a `scoreboard_heard`, none of which a fixture does.
- **The layout reads the Scoreboard, so no page is static**, and since #67 the spec says so (section 2): `/family/rylan` is rendered per request from its static file. Making one page static would mean the provider starting from the socket alone, or first paint streaming in behind a Suspense boundary, for every page.

## Finished games (#40)

- **A poll only notes work; a timer set for at once does it.** `ScoreboardAgent.onSlateTransitions` puts each final in the Agent's storage (`pending-final:<id>`) and `onSlateDateChange` notes where catch-up starts (`catch-up-from`); `recordFinals` and `catchUp` are the callbacks of one-off schedules set with a delay of 0. First paint therefore never waits on rosters or thirty scoreboards, and every good poll sets the timers again while anything is left, which is the retry.
- **Pages are told through `invalidatedAt` in `ScoreboardState`**, moved after the tags are written: at a final, at the 5-minute second invalidation and after a catch-up that recorded a game. The client component holding the Scoreboard socket (`ScoreboardProvider`, since #67) calls `useRefreshOnInvalidation(state.invalidatedAt)` (`apps/web/lib/use-refresh-on-invalidation.ts`), which calls `router.refresh()` on each change. The field is optional in the schema because state stored before it existed lacks it.
- **`schedule(when, callback, payload, { idempotent: true })`** makes a one-off schedule that a second call with the same callback and payload finds instead of duplicating. It is what lets a final's work be repeated without a second pair of timers.
- **What a finished game needs done is in `apps/web/agents/final-game.ts`**: `saveFinal`, `invalidateForFinal`, `invalidateStandingsAndTeams`, `rereadArchivedPlays`. The Game Agent (#48) calls the same functions; `rereadArchivedPlays(db, gameId)` is the 24-hour re-read and what a Replay's first open wants after it has archived.
- **`startPrediction(game)` on `ScoreboardAgent` is where #52 starts a Prediction.** It is awaited inside the poll, and so inside first paint: start the model call from a schedule, as the finals are.
- **vinext's KV cache stores a tag with a colon in it under a hash** (`__tag:__hash:...`); only `standings` and `teams` are readable in a key listing. A test names the tags it expects and compares `createKvKeySpace(undefined).tagKey(tag)` from `@vinext/cloudflare/cache/kv-key`.
- **A final invalidates about 50 player tags, one KV write each**, plus two ESPN requests for the rosters. A first visit after a full night of games does that for every game in one alarm. Not yet measured against the account's subrequest limit on Cloudflare.
- **Catch-up records only games ESPN calls final on the missed date.** It writes rows and invalidates standings and teams; it sets no timers and invalidates no players, as the spec has it.

## The Game Agent (#48)

- **Connecting a game page**, in two steps. A server component calls `readGame(id)` (`apps/web/lib/game.ts`) for first paint: a `GameSnapshot`, `{ header, delayed, archived, plays, notFound }`, already a plain object. `notFound` is the not-found page. A client component then calls `useGameStream(id, snapshot)` (`apps/web/lib/game/use-game-stream.ts`), which opens the socket and returns `{ header, delayed, archived, plays }`, current from then on: hand `header` and `plays` to `GameView`, and `delayed` is its `notice`. A client component must not import `lib/game.ts`: it imports `cloudflare:workers`; `lib/game-connection.ts` is the client-safe part.
- **The plays are not in the Agent's state.** State is the header and two flags, sent whole on each change. Plays arrive as `GameStreamMessage`s (`packages/schemas/src/game-stream.ts`): `plays` (every play, on connect), `play-added`, `play-changed`, `play-removed`. `applyGameStreamMessage(plays, message)` is the reducer and `parseGameStreamMessage(event.data)` tells them from the Agents SDK's own messages on the same socket; the hook does both.
- **The socket is what makes the Agent poll.** Render the component that calls `useGameStream` only while the game is live or about to be; a page for a game three hours off that holds a socket costs a poll every 5 minutes. A final game's Agent never polls, socket or not.
- **`header.status === "final"` comes first, `archived` about 30 seconds later**, after the last poll and once the row and plays are in D1 (at once for a game that was already over when first read). A page that turns into the Replay (which reads D1) waits for `archived`. Once archived, the plays are gone from the Agent's storage, and its snapshot and its on-connect message read them from D1.
- **The Replay's first open of a game nobody watched** is `archiveGame(id)` (`lib/game.ts`), which calls the Agent's `ensureArchived()`: one read of ESPN, the row and plays into D1, the 24-hour re-read set on the Game Agent's own timer. It answers false for a game that is not final, or final with no plays from ESPN. The Scoreboard sets a re-read of its own at a final it sees, so a watched game is re-read twice; both are the same harmless replace.
- **An intermission is a live game whose last play is `period-end`**, not a clock at 0:00: the recorded summaries have no clock in the header, so the translation's "0:00" cannot be told from a real one. If #54 finds a live summary has a clock, nothing here needs it. `readSummary()` on the Agent is where the header would be given a different source.
- **A viewer who connects just after a first-paint read waits a full interval for the next poll**, because the staleness check counts from the last poll of any kind. In a test, `await agent.getGame()`, then `connect()`, then `later(10)`, not `later(0)`.
- **ESPN's answer in a test is the recorded shootout cut short** (`live(id, plays, edit)` in `game-agent.test.ts`): the raw response with its first N plays and `status.type` made in progress, through the real parser. Play 12 is the first goal, 97 the end of the 1st, 98 the start of the 2nd. The summary is asked for as `/summary?event=<id>` and the stub answers by event id, with a 404 for an id it was not given.
- **A restart test cannot use `ESPN_FIXTURES` here**, since the only recorded summaries are a final and a scheduled game. It spies on `readSummary` on the live instance until the restart (a spy that awaits no stubbed `fetch` does not stop the eviction) and the restart itself removes the spy.
- **`vi.spyOn(env.DB, "batch")` in a test reaches the Agent's D1**: `env` from `cloudflare:workers` is the same object the Agent holds. `replaceGamePlays` is the only `batch` in a final's write.
- **An idempotent `schedule` made from inside the callback of the same name and payload finds the timer that is running**, which is deleted when the callback returns. A callback that sets itself again does it without `idempotent`.
- **A timer's payload is part of what `idempotent` matches**, so the same callback with a different payload is a second timer. The Agent's `archive` timer is set only by the poll that first finds the game final, for that reason.
- **`/tmp` filling up also breaks the agent's own shell**: every command then reports `EDQUOT` and its output is lost, though the command ran. Send output to a file under `node_modules/.tmp` and read that. On 2026-10-06 the space was held by another project's session under `/tmp/claude-1000`, not by this repo.
- **No live summary was recorded**: no game was in progress on the afternoon this was built. `record-live.ts` is still the way to get one, and a test stepping through it would sit beside the cut-short ones.

## Predictions (#52)

- **Where it is.** `ScoreboardAgent.startPrediction(game)` only notes the game in the Agent's storage (`pending-prediction:<id>`); `makePredictions`, a one-off schedule set for at once, makes one model call per run and sets itself again while games are ready. One call per run because a model call takes 8 to 25 seconds and the Agent's timers run one after another: the Scoreboard's own poll waits behind whatever timer is running. The prompt, the inputs and the reading of an answer are in `apps/web/agents/prediction.ts`; the answer's schema is `predictionOutputSchema` in `packages/schemas`.
- **For the pages (#53).** `getPredictions(db, gameIds)` reads a slate's rows as a `Map` keyed by game id (a failed attempt is in it as its `failed` row; "pick pending" is a scheduled game with no entry). `pickOutcome(prediction, final)` in `packages/schemas` says `"right"`, `"wrong"` or null from anything with `home` and `away` carrying `id` and `score`; hand it a final game only. The Scoreboard moves `invalidatedAt` when a game's row is written, made or failed, so a page that calls `useRefreshOnInvalidation` re-renders when a pick arrives. Prediction rows are not behind a cache tag: read them from D1 in the server component.
- **The AI binding has nothing local behind it.** Under `pnpm dev` every call throws "Binding AI needs to be run remotely", so after three tries each scheduled game gets a `failed` row in the local D1 (in fixture mode only 401892449 gets as far as the model; the others have no recorded summary and fail on ESPN). A page that wants a pick locally seeds the row before the game is first seen: `insertPredictionIfAbsent` keeps the row that is there. `AI_REMOTE=1 pnpm dev` makes real calls on the account cf is logged in to, about a cent for a full slate; that is how rows 18 and 19 were proved, with no deploy.
- **Declaring the AI binding makes the Vite plugin open a session with the account as the dev server starts**, whatever the binding's `remote` says, which needs a login. `remoteBindings` in `apps/web/vite.config.ts` turns that off unless `AI_REMOTE=1`. `bindings.ai({ dev: { remote: false } })` is refused outright ("do not support local development"): leave the option out. Not run on a machine with no login; what was seen is that the dev server no longer prints "Establishing remote connection".
- **The two models answer in two shapes.** `gpt-oss-120b`: an OpenAI chat completion, the JSON as text in `choices[0].message.content`, its thinking in `message.reasoning`. The llama model: the same, plus `response` already parsed to an object. `readModelAnswer` reads both. `gpt-oss-120b` is not on Cloudflare's list of JSON-mode models and honours `response_format: { type: "json_schema" }` all the same. A model's request and response schema: `cf ai get-model-schema --model <id>`; one call from the shell: `cf ai run <model> --body @request.json`.
- **Reading the gateway's log**: `cf ai-gateway logs list --gateway-id yogan-hockey --order-by created_at --order-by-direction desc`, then `cf ai-gateway logs get-request <log-id> --gateway-id yogan-hockey` and `get-response` for the prompt and the answer. The list has tokens, cost, duration and the `gameId` metadata, and no bodies.
- **In a test the binding is replaced on the instance**: `runInDurableObject(agent, (instance) => Object.assign(instance, { env: { ...env, AI: stub } }))`. The pool has no AI binding, so in every other test file `env.AI` is undefined; their games are years before the faked clock, so no Prediction is started.
- **"Two or three sentences" is counted** by `countSentences` in `packages/schemas`, which knows that "3-1-0", ".926", "A. Stolarz" and "St. Louis" end nothing. It is what failed the llama answers; nothing `gpt-oss-120b` wrote failed it.

## The pick on the site (#53)

- **The words are `apps/web/lib/picks.ts`**, tested: `pickLine` ("TOR 58%", "pick pending", or null), `slatePicks`, `recordLine`, `finalResult`, `seasonOfSlate`. ## Testing an Agent in the Workers pool

`apps/web/agents/scoreboard-agent.test.ts` is the worked example.

- **The Agent runs in the test's own isolate**, so `vi.stubGlobal("fetch", ...)`, `vi.stubEnv` and `vi.useFakeTimers` all reach it. Stubbing `fetch` puts recorded ESPN responses through the real parser and catches the ntfy pushes.
- **Fake only the clock**: `vi.useFakeTimers({ toFake: ["Date"], now })`. The Agents SDK decides what is due from `Date.now()`, so `vi.setSystemTime(...)` followed by `runDurableObjectAlarm(stub)` runs whatever schedule has come due. The alarm helper returns `false` when no alarm is set, which is how a test sees that polling has stopped. Leave `setTimeout` real, or `vi.waitFor` never ticks.
- **Set the faked clock ahead of the real one.** A schedule made by a clock that is behind is an alarm already due, and workerd fires it by itself.
- **A socket**: `routeAgentRequest(new Request("http://localhost/agents/<kebab-class>/<name>", { headers: { Upgrade: "websocket" } }), env)`, then `response.webSocket.accept()`. `onConnect` has run by the time it returns. On connect the SDK sends `cf_agent_identity`, `cf_agent_state` and `cf_agent_mcp_servers`; a write from the client is `{ type: "cf_agent_state", state }` and is answered with `cf_agent_state_error`.
- **`onClose` runs some time after `socket.close()`.** Wait for it: `vi.waitFor` on `runInDurableObject(stub, (agent) => [...agent.getConnections()].length)`.
- **A restart is `evictDurableObject(stub)`**: memory goes, storage, schedules and hibernated sockets stay. It needs a default export on the test entry, which is why the entry is `agents/test-worker.ts`. It hangs under a faked clock (switch to real timers around it) and it hangs for good once the Agent has awaited a `fetch` stubbed by the test, so a restart test uses `ESPN_FIXTURES=1` up to the restart.
- **`console.log` in a test does not reach the terminal.** `console.error` from the Agent does, so the failing-poll tests are noisy by design.
- **Biome reads a helper named `after` as a test hook** (`noDuplicateTestHooks`). Call it something else.
- **The tests of one file share Durable Object storage.** Give each test its own instance name.
- **`runDurableObjectAlarm` runs what is due and no more.** A schedule a callback sets for "now" waits for the next call, so after a poll that leaves work a test calls it once more (`visit()` in `scoreboard-finals.test.ts`). It returns true whenever any alarm was set, due or not.
- **A test's first call to an Agent starts it cold**, 2 to 5 seconds when other worktrees are running their suites, against Vitest's 5-second default. `lib/scoreboard.test.ts` timed out in the full suite for that reason and has a longer timeout; a test that fails only in the full run is likely this.
- **A hook on the Agent can be spied on**: `runInDurableObject(stub, (instance) => vi.spyOn(instance, "method"))` reaches the live instance, since it is in the test's isolate.

## ESPN

- **Fixture mode is `ESPN_FIXTURES=1`**, read by `packages/espn` from `process.env` on every read. Under `pnpm dev` and `pnpm build` the Worker never sees the shell's environment, so `apps/web/vite.config.ts` compiles the variable in with `define`: set it when the dev server starts, and restart to change it. In Vitest, the Workers pool included, `vi.stubEnv("ESPN_FIXTURES", "1")` works. A build without it contains no recorded response; keep the test written out inside `read` in `client.ts`, because behind a function the bundler keeps the fixtures.
- **Fixture mode answers only what is recorded**: the current scoreboard (the slate of 2026-10-06, nine games), the scoreboard of 2026-10-03, standings, the team list, and Toronto (team 21) with its schedule. Since #35 also: two game summaries (401803652, a finished shootout from April 2026; 401892449, Nashville at Toronto while still scheduled), Auston Matthews (4024123) and the goalie Anthony Stolarz (3067313) each with profile, career and game log, and the search for `mar`. Anything else is an `EspnFetchError` naming the missing file. To add one, add a sample to `READS` in `packages/espn/check/samples.ts` (the one list the recorder and the daily live check share) and run `pnpm record:fixtures`.
- **No recorded slate has a live game yet.** Every game in `scoreboard.json` is scheduled and every game in `scoreboard-20261003.json` is final; nothing was on when they were recorded. The live and postponed cases in `scoreboard.test.ts` change the status of a recorded game. Run `pnpm record:fixtures` during an evening of games, then `pnpm test -u`, and tickets that need a mixed slate get a real one.
- **Recording rewrites `scoreboard.json` with whatever is on**, so the snapshots and the literals in the tests that name its games change with it. The dated slate and the rest move only as the season does (standings, records, the schedule's results).
- **ESPN answers an unknown team id with HTTP 400**, not 404. `EspnFetchError.notFound` covers both; use it for the not-found page.
- **A scoreboard asked for by date has no `day`**, and a range (`dates=20261005-20261006`) is a 400. Catch-up fetches one date at a time.
- **ESPN names the same thing differently by endpoint.** A side's overall record is type `total` on a slate still to be played and `ytd` on a finished one and on a schedule; a score is `"3"` on the scoreboard and `{ value: 3 }` on a schedule; the scoreboard sends one `logo`, everything else a list of `logos`; the season type is inside `season` on the scoreboard and beside it on a schedule. `espn-game.ts` and `espn-team.ts` absorb all of it into one `Game` and one `Team`.
- **Standings come from `standings?level=3`** (conference, then division). The default response has no divisions. `standingsView` in `packages/schemas` ranks the rows itself, so ESPN's order is not relied on.
- **Team stats come with team detail** (`teams/{id}?enable=roster,stats`): the overall record's stats carry goals, power play and penalty kill. The separate `teams/{id}/statistics` and `teams/{id}/roster` endpoints are not used.
- **The team schedule is asked for with `seasontype=2`**, the regular season; `1` is the preseason and `3` the playoffs, which nothing asks for yet. It is 1.1 MB for 84 games.
- **Playwright reuses a dev server that is already running** outside CI. One started without `ESPN_FIXTURES=1` gives the smoke tests live ESPN; stop it first.
- **`pkill -f "[v]ite dev"` does not match the dev server** `pnpm dev` leaves listening (its process is `node`), and it would match other worktrees' servers if it did. Stop yours by port: `kill $(ss -ltnp | grep ':5234' | grep -o 'pid=[0-9]*' | cut -d= -f2)`.
- **A search is recorded under its query** (`search-mar.json`), so in fixture mode any other query is an `EspnFetchError`. A smoke test of the players page searches for "mar".
- **A scheduled game's summary is recorded once.** `record-fixtures.ts` keeps `summary-401892449.json` if it exists, because recording it again after the game would replace the pre-game summary with a finished one. To get another scheduled game, add it to `RECORDED_ONCE` before it starts.
- **No in-progress summary is recorded yet.** The live probe's `probe-*.jsonl` held one `start` line each when #35 ran, and it logs diffs, not whole polls, so it could not have supplied one anyway. `node packages/espn/scripts/record-live.ts <eventId> [polls] [seconds]` writes whole polls of a live game to `fixtures/live/`; run it during a game and the Game Agent's diff tests have a real sequence. It was run against a finished game only.
- **The summary header's status has only `type` for a scheduled and a finished game**: no `period`, no `displayClock`. `translateGameSummary` reads them when they are there and otherwise takes the period from the last play (then the line score) and the clock as "0:00". Whether a live summary carries them is not yet seen; if it does not, the live clock has to come from the Scoreboard's `Game`.
- **A play's clock counts up** (a period starts at 0:00, overtime ends at 5:00), where the scoreboard's clock counts down.
- **A shootout is period 5 with every play at 0:00.** Its goals have `scoring: true` and do not move the running score, and the plays after overtime read one goal lower for the eventual loser than the plays before (3-3 at the end of overtime, then Dallas 3, Buffalo 2 through the shootout Dallas won, in 401803652). Take no score from plays.
- **A penalty is a play whose ESPN type has `penaltyMinutes`.** Its type abbreviation is the infraction's name with capitals and spaces ("Delaying Game-Puck over glass", "Fighting (maj)"), and its participants have no role. "End of Game" has no abbreviation at all, so its `type` is made from its wording: `end-of-game`.
- **In this fixture list order and `sequenceNumber` order agree.** The order the site keeps is the list's; a test swaps two plays to prove it.
- **The summary header's team has no `shortDisplayName` and no `logo`** (it has `name` and `logos`); the boxscore's team has both but no dark logo. The header's is the one translated.
- **ESPN's `atVs` is wrong for some road games** in the last five games and the game log ("vs" for a game played away). `homeTeamId` decides home or away.
- **A summary's last five games and goalies exist only before the game.** A finished game's `pregame` has standings, injuries, leaders and the season series, with `lastFive` and `goalies` empty. Early in a season the last five include preseason games.
- **Stat tables carry their own columns.** A skater's and a goalie's career and game log have different columns, and ESPN's labels mislead ("SOG" in a skater's career is shootout goals), so `PlayerCareer` and `PlayerGameLog` are `columns` plus rows of display strings. A season split between clubs has a row per club and then a totals row whose `team` is null.
- **A player yet to play in the NHL has a profile and turns up in search, and his stats and game log are 404s** (Sam O'Reilly, 5216901). `getPlayerCareer` and `getPlayerGameLog` answer an empty table for a 404; the profile is what says a player does not exist.
- **The game log is the latest season he played**, so before his first game of a new season it is all of last season (69 games for one player on 2026-10-06). `PlayerGameLog.season` says which; a "recent games" list takes the first few.
- **An unknown athlete or event id is a 404**, where an unknown team is a 400. `EspnFetchError.notFound` covers both. A search that finds nobody is a 200 with no items.
- **Athlete stats and game log answer on `site.web.api.espn.com`**; the profile and search on `site.api.espn.com`.
- **A name exported from two files of `packages/schemas` fails typecheck at the index** (`export *` twice). `SeasonRecord` is the picks' record; a team's is `TeamRecord`.

## The daily live ESPN check (#36)

- **Run it: `pnpm check:espn`.** It fetches live ESPN (15 or 16 requests, about five seconds), prints a line per endpoint, writes the run to `espn-check.json` (gitignored; `--summary <file>` names another) and exits 1 if anything failed. It is no part of `pnpm test` or CI: it needs the network, and ESPN being down must not fail a pull request.
- **Read a failure by its first word.** `PARSE <endpoint>` is the one that matters: ESPN answered and the answer is not the shape the site reads. The lines under it are Zod's, `path.into.the.response: what is wrong`, the path counted from the top of ESPN's JSON. Look at that path live (`curl -s '<the url printed>' | jq '.children[0].children[0] | keys'`, never the whole response), fix the schema and the translation in `packages/espn/src`, then `pnpm record:fixtures` and `pnpm test -u` so the fixtures hold the new shape. `FETCH <endpoint>` means ESPN or the network gave no answer after three tries (a 4xx is not retried: it is ESPN's answer; a 200 whose body is not JSON, such as a block page, counts as a fetch failure); one that passes the next day needs nothing done, and one that is a 404 every day means ESPN moved the endpoint.
- **`not checked:` lines are not failures.** The summaries of a live and of a scheduled game are chosen from today's slate when the check runs, so at 16:17 UTC there is usually no live game to check, and on a day without games neither. A live summary has still never been through the parsers (see the ESPN notes); a manual run during a game (`gh workflow run espn-check.yml`, or `pnpm check:espn` at home) is how to find out.
- **`packages/espn/check/samples.ts` is the one list of requests**, shared by the recorder and the check. `READS` is typed to have an entry for every builder in `endpoints`, each with its `translate*` function and at least one sample, so a read added to `endpoints.ts` fails typecheck until the check covers it. A read that built its URL without `endpoints` would escape, and `read()` in `client.ts` takes only an `Endpoint`.
- **The check calls the translations, not the `get*` reads**, so a career table or a game log that is a 404 fails the check, where the site reads it as an empty table.
- **The workflow is `.github/workflows/espn-check.yml`**, daily at 16:17 UTC and by hand (`gh workflow run espn-check.yml --ref <branch>`). It runs `pnpm check:espn` and then `packages/espn/scripts/report-check.ts`, which is where the issue and the push are decided (`check/report.ts`, tested with `gh` and `fetch` stubbed). `--dry-run` on that script prints the `gh` commands and the push without running them: `node packages/espn/scripts/report-check.ts --dry-run`.
- **One open issue at a time, found by its exact title**, "ESPN daily check is failing". A failure opens it (labelled `needs-triage`, making the label if the tracker has none) or comments on it; the first pass after a failure comments that it cleared and sends a push, both listing what that run did not check; later passes say nothing. Nothing closes it but a person, because a parse failure can depend on what was on that day. Rename the issue and the next failure opens a second one. Where things stand is read from hidden marks (`<!-- espn-check: failed -->`, `<!-- espn-check: cleared -->`) in what the check wrote.
- **The push needs the `NTFY_TOPIC` Actions secret** (`scripts/account-setup.sh`). Without it the run carries a notice, "ntfy push skipped", and the issue is still filed. A push goes out on every failing day, not only the first.
- **Not yet run on a runner.** When #36 was built, Actions could not start a job on this repo (billing), so the workflow was checked with `actionlint` only. Unproved until a run: that `GITHUB_TOKEN` with `issues: write` may create the `needs-triage` label, and how late GitHub starts the schedule.
- **Node will not run a `.ts` file under `node_modules`** (`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`), so a scratch script in `node_modules/.tmp/` that imports the packages has to be `.mjs`.

## The look: `packages/ui` and the shell (#38)

- **The dashboard is the living sample** of the Reference UI's layout (`apps/web/components/dashboard/`), and `/skeleton/dashboard` draws it from the invented slate. `/skeleton/ledger`, the shell's sample of invented rows, went with #47.

Secondary text is the foreground at an opacity, never a grey: `text-foreground/70` a note, `/60` an idle link or a second line, `/50` a column header or a count, `/40` an aside. Body text is 13px Geist Mono, set on `<body>`; the only other sizes are 10px (column headers, footer, badges, `LedgerDetail fine`), 14px (wordmark) and 16px (scores). `--radius` is 0: nothing is rounded.

- **Playwright runs one test at a time** (`workers: 1`). The tests share one dev server, one D1 and one Agent, and two browsers at once lose clicks and state to each other.

## A page: `/nhl` is the pattern (#42)

- **The shape of a page.** `searchParams` is a promise; await it and hand it whole to one pure function in `apps/web/lib` (`readNhlPage`) that returns what the page shows, every unknown value already replaced by its default. A second function (`nhlHref`) writes the URL back with the defaults left out, so each tab and view has one address. Both are tested in Vitest, as is anything else a page would otherwise work out inline (`apps/web/lib/standings-table.ts`).
- **A title that depends on the query string** is `generateMetadata({ searchParams })`, calling the same read function. vinext passes `searchParams` to it as it does to the page.
- **Each tab's data is read by its own async component** in the page file, so the Teams tab never reads the standings.
- **Two rows of `UrlTabs`** share one `<div className="space-y-2">`, so the shell's 32px spacing applies to the block and not between the rows; the first row sits in a `SectionHeader` given `className="mb-0"`. Each `UrlTabs` needs its own `label`, which is also how a Playwright test tells them apart (`getByRole("navigation", { name: "NHL", exact: true })`).
- **A standings table anywhere is `StandingsLedger`**, given one `StandingsTable` from `standingsView`; the dashboard's can be the same component. `TeamName` puts both the full name and the abbreviation in the markup and shows one, so Playwright's `toHaveText` sees "NYRNew York Rangers": match with a regular expression.
- **Eight standings columns fit a 390px phone without scrolling** once the team is its abbreviation. `className="w-full"` on the team's `LedgerColumn` gives that column the slack, which keeps the figures together and lined up from one stacked table to the next; `min-w-8` on the rank column does the same for the team names when a table reaches rank 10.
- **`cn` and the other class helpers are dependencies of `packages/ui` only.** A variant a page needs goes into the primitive (`LedgerCell tone="positive"`, `LedgerRow cutoff`), not into a `className` built in the app.
- **ESPN abbreviates Utah as "UTA" in the standings and "UTAH" in the team list.** Each is shown as ESPN sends it.
- **A test that opens several addresses cold gives each its own context** (`browser.newContext()`, as `e2e/nhl.spec.ts` does; `baseURL` still applies), which is a pasted link exactly and keeps to one hard navigation per page.
- **Re-rendering on a final needs nothing from the page.** It holds no client state, so `router.refresh()` from whatever holds the Scoreboard socket re-runs it against the cache. The refresh shows the new standings only once the `standings` tag has been invalidated for that final.

## The game page's parts (#49)

- **`/skeleton/game` and `e2e/game.spec.ts` are gone** (#51): the Replay at `/nhl/games/401803652` is the page that draws the recorded shootout, and `e2e/replay.spec.ts` carries what the sample's test checked.
- **A game page renders one component**: `<GameView header plays tab pathname pick />` from `apps/web/components/game/game-view.tsx`. `header` is a `GameHeader`, `plays` every play so far in order, `tab` is `gameTabFrom((await searchParams).tab)`, `pathname` the page's own path (the tabs are `UrlTabs` links back to it), `pick` whatever "the pick" tab shows. It is a client component and keeps two things itself: the picked play and the key-plays toggle. Both survive a change of tab, because the tab is a soft navigation.
- **The Game Stream feeds it the Agent's state as it arrives; the Replay feeds it `plays.slice(0, playhead)`.** With no play picked the focus is the last play of `plays`, so a growing list follows the game and a playhead steps through it. The overlay's score, shots, period and clock come from `header` alone (never from plays), so a Replay showing the score at its playhead passes a header with them changed. `status` replaces the words over centre ice ("End of 2nd") and `notice` adds a warning under them ("Updates delayed"). `selectedId` and `onSelect` are for a page that must hold the pick itself; leave them out otherwise.
- **The parts are usable alone**, all props and no state: `GameRink` (`header`, `plays`, `drawn`, `focus`, `status`, `notice`), `Rink` (`plays`, `focus`), `PeriodTimeline` (`game`, `plays`, `ticks`, `focusId`, `selectedId`, `onSelect`), `PlaysList`, `ScoringSummary`, `KeyPlaysToggle`. Each takes every play as `plays` and the ones to show (key plays or all) separately, because placing a shootout tick and working out the ends both need the whole game.
- **ESPN's coordinates are fixed to the building**, so `rinkPoint` only turns y over; nothing is mirrored by period. Which end a team shoots at changes every period and the home team's first end differs by game, so `attackedEnd(plays, homeTeamId, teamId, period)` reads it from the shots and answers null before the first one. The evidence is in `docs/spec.md`, Unverified row 16.
- **The rink is drawn in feet** (`RINK` in `apps/web/lib/game/rink.ts`; viewBox 204 by 89, the Reference UI's), and everything laid over it is placed in `cqw`, fractions of the rink's width, inside an `@container`. Change the overlay by those fractions, not by viewport breakpoints: beside the sidebar at 768 the rink is narrower than on a 640 phone. An end-zone circle spans 8.8% to 23.5% of the width and 8.4% to 42.1% of the height; the blue lines are at 37.75% and 62.25%; the centre circle spans 42.65% to 57.35%.
- **The timeline's widths are minutes**: 20 a period, 5 for overtime (20 in the playoffs, `seasonType` 3), and a shootout, which has no clock, the room of 8 with its plays spaced in order. `layoutTimeline(plays, game)` returns the periods and each play's place from 0 to 1.
- **The overlay's type is the Reference UI's, outside the ledger's sizes**: a 60px score, a 12px "LIVE", scaled down with the rink. Its corners are the ledger's: the reference rounds the caption, the timeline and the ticks, and the site rounds nothing.
- **`apps/web` has no `cn`**; it is a dependency of `packages/ui` only. The game components build class strings by hand.
- **A finished game's last play is "Game End"**, with no coordinate, so a Replay opened for browsing has a caption and no ringed dot until a play is picked.
- **Logic tests that need the recorded game** use `recordedShootout()` and `play({...})` from `apps/web/lib/game/test-plays.ts`.
- **Measuring the game page against the Reference UI**: the reference's rink is `svg[role=img]` at `/prototype/game?variant=C` on port 4517, the sample's is `[data-slot="rink"]`; every part of the sample has a `data-slot` (`rink-score`, `rink-status`, `rink-caption`, `rink-end`, `rink-mark`, `period-timeline`, `timeline-tick`, `play-row`). The reference page has no shell, so its rink is 1120px wide where the sample's is 1200 at 1440: compare fractions of the rink's width, not pixels.

## The game page: scheduled, live, final (#50)

- **The states** are `gamePhase(status)` in `apps/web/lib/game/page-state.ts`: `scheduled` (also a postponed game), `live`, `finished`. `GamePage` (`components/game/game-page.tsx`, a client component given `key={id}`) draws whichever the newest status says: the server's snapshot until the socket is open, the stream's header after.
- **What opens the socket** is `streamStarts(snapshotStatus, scoreboardStatus)`: a snapshot that is live, or a scheduled one whose game the Scoreboard (`useScoreboard()`) reports live or final. `GamePage` keeps the answer in state once true, because the slate moves to another day under an open page and the `router.refresh()` at a final hands it a new snapshot. `GameStream`, inside it, is the only caller of `useGameStream`. A game final when opened never gets a socket.
- **With the socket just opened the page still shows the matchup** until the Agent's header says live, so the rink never shows a scheduled header with a 0-0 score.
- **The words over centre ice are `streamReading`**: "End of 2nd" when the last play is `period-end`; the header's clock when it has one; when it is "0:00" (every recording), the Scoreboard's clock for the same game and period ("2nd 12:34", time left, as the ticker shows it); failing that the period alone. "Updates delayed" is its `notice`. #54 settles the clock against a real game: if a live summary carries a clock, the first rule already takes it.
- **`FinishedGame`** (`components/game/finished-game.tsx`) draws the Replay (see "The Replay (#51)"): props `gameId`, `header`, `plays`, `archived`, `notice`, `tab`, `pathname`, `pick`. A game that ends on an open page gets the stream's plays and `archived` turning true about 30 seconds later; a game opened after its final gets the snapshot's. Going from live to finished remounts `GameView`, so the picked play and the every-play choice start again; the Replay holds them itself anyway.
- **The pick is `GamePick`** (`components/game/game-pick.tsx`, drawn by the server from a made Prediction). The page renders it once and `GamePage` shows it as "The pick" section of the scheduled page and as the tab afterwards. See "The pick on the site (#53)".
- **The matchup facts are a cached read**, `cachedGamePregame(id)` in `lib/espn.ts` (15 minutes, tagged `game:<id>`), not part of the Agent's snapshot: only a scheduled page asks for it, and a failure draws nothing instead of failing the page. `GameMatchup` draws it; `MatchupRink` is the scheduled rink, sharing `GameRink`'s overlay places so the ice does not move at the switch.
- **An id that is not digits is not found without waking an Agent** (`findGame`, `lib/find-game.ts`), so a mistyped address makes no Durable Object.
- **Driving a game in Playwright**: `e2e/game-driver.ts`. `driveGame(page, id)` passes the Scoreboard's socket through (and pushes the slate with the game changed: `scoreboard({ status: "live", period, clock, scores })`) and answers the Game Agent's socket itself (`agent(state, plays)`, `message(...)`); `recordedGame(baseURL)` gets the shootout's plays from that game's real Agent over a Node `WebSocket` and renames its teams to the scheduled game's, since the only page that starts scheduled in fixture mode is 401892449. `node scripts/game-page-shots.ts` uses the same driver for the shots in `docs/design/game-page/`. Node runs the `.ts` itself, but not from under `node_modules`.
- **`getByText` on a status can wait forever**: the same words are in a hidden timeline label. Filter the `[data-slot="rink-status"]` locator by text instead.
- **A snapshot with no header and no `notFound`** (seen once, on a finished game's first request after a cold start, right after workerd's "RPC connection broken ... exceeds size limit" line; never reproduced) is handled since #51: `findGame` reads once more at once, and a second empty answer or a second throw is `{ state: "unreadable" }`, which the page says in words ("This game could not be read just now") instead of answering 500. `findGame` returns a `GameLookup` (`found`, `missing`, `unreadable`), not a game or null.

## The Replay (#51)

- **The rules are `replayReducer` in `apps/web/lib/game/replay.ts`**, tested in `replay.test.ts`. The playhead is an index into every play of the game, or null for the whole game laid out, which is how a Replay opens and where playing ends. It is never an index into the Key plays, so the key-plays toggle cannot move it; the toggle decides only what a step lands on (the Key plays, or every play once every play is listed). The game's last play, "Game End", is the whole game: stepping or clicking onto it is the end.
- **Play from the whole game starts again at the first play.** A step is 1.2 seconds at 1x (`stepMilliseconds`), 2x and 4x divide it; the game's real gaps are not followed.
- **`Replay` (`components/game/replay.tsx`) gives `GameView` the game at the playhead**: `plays` up to it, `upcoming` for the rest (faint ticks that can be clicked; they also keep the timeline's layout and the rink's ends where the whole game puts them), `headerAt` for the score and shots, `statusAt` for the words over centre ice, and the controls as `transport`, which takes the place of the timeline's hint. `GameView`'s `everyPlay` and `selectedId` are controlled by it.
- **A shootout play's running score is not the game's**: in the recording every shootout play says 3-2 through a 3-3 shootout. `headerAt` takes the score from the last play before the shootout, and the final from the header alone (only the header gives the winner its extra goal).
- **ESPN has no running shots**, so `headerAt` counts shots on goal and goals up to the playhead, shootout left out. For the recording that makes 53 by the end where the header says 28 and 24, so the count can be one off just before the end; the whole game shows the header's own.
- **Where the plays come from** is `lib/replay.ts`. `replayGame(found)` in the route: a snapshot the Agent calls archived already carries D1's plays (the Agent reads them with `getGameWithPlays`), so nothing more is read; a final one that is not archived gets `replayPlays(id)`, which reads D1, and only if the plays are missing calls `archiveGame(id)` and reads D1 again. The second open is one D1 read and no ESPN.
- **The header is still the Game Agent's**, not D1's: a `games` row has no shots, names or "Final/SO". For a final game the Agent answers from its stored state without asking ESPN.
- **A page that saw the game end** shows the stream's plays for browsing with the transport's place held (`ReplayPending`), and `FinishedGame` calls the Server Action `loadReplayPlays(gameId)` (`app/nhl/games/[id]/actions.ts`): at once when `archived` turns true, otherwise every 10 seconds for two minutes. It becomes the Replay when plays come back. This path has no browser test: the driven game in `e2e/game-driver.ts` is the scheduled fixture, which the real Agent will never archive.
- **`ensureArchived()` answers false while the last poll is still to come** (an `archive` timer with `lastPoll: true`). Without that, any open of the page in the half minute after a final, including the `router.refresh()` the Scoreboard causes on the page that watched it, wrote the game before ESPN's closing plays.
- **A timeline tick and its play's row have the same accessible name** ("2nd 4:24 Esa Lindell Goal ..."), so `getByRole("button", { name })` matches two. Find a tick as `[data-slot="timeline-tick"][aria-label^="2nd 4:24 "]`. Ticks for plays not yet reached have `data-upcoming`.
- **The whole game has one more tick than Key plays** (75 for the recording's 74): the play in focus is always drawn, and "Game End" is not a Key play.
- **`node scripts/replay-shots.ts [baseURL] [outDir]`** takes the shots in `docs/design/replay/` (opened, playing, end; light and dark; 1440 and 390) against a fixture-mode dev server.
- **This machine has no `lsof`.** A script that stops a server with it stops nothing and says nothing; Playwright then reuses the stale server, and with `.cloudflare/state` deleted under it every spec fails. Use the `ss -ltnp` line in the Playwright notes.
- **The recorded scheduled game lists Sergei Bobrovsky under Toronto** because ESPN's `goalies.homeTeam` (`teamId` 21) does. The translation was not at fault; since #51 it gives each team the list carrying its `teamId` rather than trusting the `homeTeam`/`awayTeam` key.

## A page with an id: the team page (#43)

- **A browser never gets an async title in `<head>`.** vinext does what Next.js does: the `<title>` from `generateMetadata` is streamed in a hidden `<div>` at the end of `<body>` and stays there, and `document.title` reads it. Only a user agent on vinext's list of link previews and crawlers gets it in `<head>`. So `toHaveTitle` proves a title; a search of the raw HTML's `<head>` needs a bot's user agent (`e2e/team.spec.ts` sends Twitterbot's).
- **Do not call `notFound()` in `generateMetadata`.** vinext answers 200 for it when the metadata is streamed. Return a title and let the page call `notFound()`: `/nhl/teams/leafs` is then a 404. The title of a not-found page is the layout's default ("Yogan Hockey"), whatever `generateMetadata` returned.
- **A `not-found.tsx` beside the page works** and is drawn inside the shell: `app/nhl/teams/[id]/not-found.tsx` is "Team not found".
- **The page and its title share one read through React's `cache`** (`const team = cache(findTeam)` in the page file). `findTeam` (`apps/web/lib/find-team.ts`) is the pattern for a page with an id: null for an id that cannot be one (`packages/espn` throws a `RangeError` for anything but digits, before asking ESPN) and for ESPN's "no such thing", an error for everything else. `EspnFetchError` keeps its class through `unstable_cache`.
- **Fixture mode cannot show an unknown team**: every team but Toronto is a missing fixture, which is an error and not a 404. The smoke test's not-found case is an id that is not digits; the 400 from ESPN is covered in `find-team.test.ts`.
- **A time in the visitor's zone is `LocalTime`**: see "Live scores on a page". A screenshot or a Playwright test sees the browser's zone: set `timezoneId` on the context (`test.use({ timezoneId })` in `e2e/live.spec.ts`) and assert that zone's time, which has no "ET" after it.
- **The team page's cached `nextGame` can be an hour old**, so it may name a game that has started or finished. `nextGame()` and `liveGame()` in `apps/web/lib/team-schedule.ts` ask the Scoreboard, and `TeamNow` (a client component on `useScoreboard()`) draws the banner or the Next Game card from them, so both change without a refresh. Anything that shows "next" or "live" for one team should use them.
- **`GameLedger` needs about 670px from `sm` up** (its columns are fixed). In half of a two-column grid at 1440 it loses the home score off the right edge, so the banner spans both columns (`xl:col-span-2`).
- **Links to a game and to a player are `gameHref` (`lib/scoreboard-view.ts`, which takes a `Game` too) and `playerHref` (`lib/roster.ts`)**, beside `teamHref`.
- **One row of figures under a header** (the team's record, its season stats): give the last column `w-full` so the figures stay together at the left, as the standings give it to the team. A ledger of names across the whole 1200px page is too wide to read across; the roster keeps to the first column of `grid gap-8 xl:grid-cols-2`.

- **A heart in a row that links** (#45): the row's link covers the row, so a button in a later cell needs `relative` to be clickable. `RosterLedger` takes it as `action`, `TeamHeader` as `action` too.
- **The dev server's HTML is four times the size of production's** (980 KB against 222 KB for the 84-game schedule): React's development payload carries every server component's props. Measure page weight on `pnpm build` and `pnpm exec vite preview --port <PORT> --strictPort` in `apps/web`; build with `ESPN_FIXTURES=1` to preview fixture mode.
- **No recorded slate has a live game**, so the "Playing now" banner cannot be reached in fixture mode. The shots in `docs/design/team/live-banner-*` were taken with one recorded game made live inside `TeamNow` for the shot and changed back. `StaticScoreboard` around a component is the way to do it in a sample page.

## Server Actions, `searchParams` and links (#44)

`apps/web/app/players/` is the worked example: `page.tsx`, `actions.ts`, `player-search.tsx`.

- **A Server Action that reads** is a `"use server"` file exporting an async function, imported and called by a client component inside `startTransition`. It needs no `refresh()` (that is for an action that changes data). Have it return a value for every outcome, a failed ESPN read included, so that the call failing means only that the call failed.
- **A Server Action called from a tab older than the last deploy resolves with `undefined`**, without throwing. Each build has a new `x-vinext-rsc-compatibility-id`; vinext's client drops an answer whose id is not its own and hard-navigates to the URL the action was called from. So: treat no answer as a failure, and put what the action was asked into the URL before calling it, so the reload lands on a page the server can render by itself. A rebuild of unchanged code is enough to see it: `pnpm build`, `vite preview`, open the page, build and start again, use the page.
- **The server half of a file reaches the client if a client component imports it.** `lib/players.ts` imports the cache; a client component may import its types (`import type`) and nothing else. What both sides need at run time lives in `lib/player-search.ts`.
- **`history.replaceState` changes the URL and fetches nothing** under vinext: no RSC request, no re-render. The search box uses it to keep `?q=` in step with the typing; a reload then renders that search on the server.
- **A client component keeps its state when only `searchParams` change**, so a link from `/players?q=mar` to `/players` would leave "mar" in the box. A `key` from the server does not cure it: once the client has rewritten the URL itself the server's key is the one it already had, and a key that is new on every render remounts the box on the `router.refresh()` the shell makes when a game goes final. The box reads `useSearchParams()` and, in an effect that also depends on the server's `initial`, starts anew from `initial` when the URL's search is not what is typed (whether the hook follows `replaceState` under vinext was not established; the effect is right either way).
- **A page that reads nothing from the request and omits `force-dynamic` is cached for a year** in a production build (`x-vinext-cache: HIT`, `s-maxage=31536000`); `pnpm dev` does not show it. Reading `searchParams` makes a page dynamic by itself. Check a new page with `curl -sD - -o /dev/null` against `vite preview`.
- **`next/link` prefetches every link on screen in a production build**, and the prefetch renders the page: ten search results were ten player pages, thirty ESPN reads, per search. `pnpm dev` does not prefetch, so only a build shows it. Rows of a list take `prefetch={false}`.
- **A `not-found.tsx` beside a page takes over when the page calls `notFound()`**, inside the shell, with a 404. Its title comes from its own `metadata` export; what `generateMetadata` returned for the page is not used.
- **Async `generateMetadata` lands in `<head>`** (`/players/4024123` is titled "Auston Matthews"). Wrap the loader in React's `cache()` so the title and the page load the player once.
- **In fixture mode an unknown numeric player id is a 500**, since a missing recording is not ESPN's 404. `/players/abc` (not an ESPN id, never asked for) is the 404 a test can reach; against live ESPN `/players/999999999` is a 404 too.
- **A `Ledger` with a few numeric columns spreads them across the page.** End the header with `<LedgerColumn className="w-full" />` and the figures sit together at the left (the Season ledger of a player page).
- **A rule above a totals row goes on its cells** (`[&>td]:border-t`): with collapsed borders a row's own top rule loses to the rule under the row before it. Setting a border colour on a `LedgerRow` recolours the rule under it as well; name the side (`border-t-foreground/20`).
- **A text field is 16px on a phone** (`text-base md:text-[13px]`): Safari zooms the page when a smaller one takes focus.

## The dashboard (#47)

- **`/` is `<Dashboard />`** (`apps/web/components/dashboard/dashboard.tsx`, a server component): `TonightGames` (client: the socket and the favorite teams), then a two-column grid of `FamilyLedger` (server), `DashboardFavorites` (client) and one compact `StandingsLedger` per conference (server). The logic is `apps/web/lib/dashboard.ts`, tested: `tonightGames` (the order), `tonightSummary`, `gamePlayingNow`, `familyTotals`, `topOfConferences`.
- **Where the picks go.** `Dashboard` takes `picks` (game id to the note's line, a string or an element; a game with no entry shows nothing) and `record`, and passes them to `TonightGames`. They cross from server to client, so they are data and elements, never functions. `app/page.tsx` fills them from D1 (see "The pick on the site (#53)"); `/skeleton/dashboard?picks=1` fills them with invented ones. The picks are as old as the server's render: a new one appears at the refresh the Scoreboard causes when the row is written.
- **The same pick on any other game row** is `GameLedger`'s `pick={(game) => ...}` (`/nhl/live` passes it too). It is drawn in the note column after the favorite marker (`[data-slot="game-pick"]`) and, on a phone, takes the venue's place in the small line under the status, where there is room for one or the other.
- **`GameLedger fitted`** is for a ledger that stands alone: from `sm` the columns size to their contents and the note has the rest, cut short with `max-w-0 truncate` (a cell that wide never widens its column, even in an auto-layout table); from `xl` the columns are the percentages the Reference UI's table measures at 1440. Stacked ledgers (`/nhl/live`) keep the fixed widths so they line up.
- **The Scoreboard's games carry `broadcasts` since #47**, optional in the schema because state stored before then has none until the next poll that finds a difference.
- **A one-column grid needs `grid-cols-1`**: a bare `grid` sizes its implicit column to the widest child, so a ledger with a `whitespace-nowrap` line made every block wider than a phone. With `grid-cols-1` the column is `minmax(0, 1fr)` and a wide ledger scrolls inside its own box.
- **`useFavoritePlayers(limit)` passes over a dead id** (`favoritesToShow`): a favorite that resolves to nobody gives its place to the next, so the dashboard shows four when four exist. One that could not be read just now keeps its place.
- **The favorites block is the browser's, so the blocks under it move** when its rows arrive (the server cannot know how many). Standings sit under it on a phone and beside Family's row on a wide page; nothing was done about the shift.
- **The Family row has no room for +/- and P/GP** (#86, tried and left). Half a page at 1440 is 584px; six figure columns leave the team column 263px, the last-game line (289px) wraps, the name wraps too, and the row goes from 52px to 71.5px. At 390 the table is 368.5px in a 358px box and the row 130px for 91px. Both figures are on `/family/<slug>`.
- **A compact `PlayerLedger` names the team in full** to a screen reader and on hover: an `<abbr title>` holding the abbreviation (`aria-hidden`) and the name (`sr-only`). Playwright's `toHaveText` sees both.
- **A new spec file that sorts first meets a cold Scoreboard.** `e2e/dashboard.spec.ts` is the first to run; it passes from cold because the layout's first paint asks the Scoreboard, which polls before answering. Deleting `apps/web/.cloudflare/state` under a running dev server leaves a Scoreboard that never answers ("Today's games could not be read"): stop the server first.
