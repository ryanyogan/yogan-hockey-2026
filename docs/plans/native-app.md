# Shared API and native app plan

> **Superseded on 2026-10-11 by [#123](https://github.com/ryanyogan/yogan-hockey-2026/issues/123).** The React Native app and its Hono API are cancelled: the installed site (a PWA) is the mobile app, and ADR 0007's "no API" stands. Kept for its research on notifications and the socket contract; nothing below is a plan to build.

Planning for [#110](https://github.com/ryanyogan/yogan-hockey-2026/issues/110). Research checked **2026-10-11** against official documentation and repository commit `838f0ce`. This is a proposed implementation sequence, not an implemented API or authorization to start it. No native app, auth provider, push delivery, or new backend is installed by this change.

## Recommendation and first release

Add Hono routes to the existing Worker and an Expo React Native app to this pnpm monorepo. Keep the Scoreboard and Game Agents as the live authorities, ESPN as the only sports source, and existing D1 Predictions as the only picks. Web server components and Server Actions continue calling the shared server functions directly. A native client needs an HTTP contract; the web does not need a network hop to itself.

Ship an invite-only family pilot: today's scores, one game's score and plays, player search/profile and team selection, account favorites, and opt-in goal/final notifications. Home keeps stable scheduled-start/id order as agreed in #111; favorites mark rows without moving them. The child signs in with username/password; an authenticated parent provisions and recovers the child account. Recommend **Clerk for this first release**, with application-owned parent/child authorization in D1. Better Auth remains a viable ownership-oriented alternative, with extra work described below.

Assumptions: “home-screen scores” means the app's Home screen. Device home-screen widgets, lock-screen Live Activities, full Replay controls/rink, all standings/stat tables, public child self-signup, chat and social features are later work. Support both iOS and Android in the code, with the son's actual device selected for the first distribution build. None of these assumptions require halting this plan; record changes before implementation tickets are opened.

The one unresolved architectural decision is background polling for notifications. [ADR 0007](../adr/0007-one-worker-no-api-two-agents-three-stores.md) explicitly rejects polling with nobody watching. A push-capable app needs bounded demand that survives the app closing. The proposed exception below is for Ryan to resolve on #55 before that ticket starts. Scores and foreground subscriptions can ship independently.

## Proposed REST contract

All paths below are proposals under `/api/v1`. IDs are opaque strings preserving ESPN ids; validate supported NHL resource ids before reaching Agents. Times are ISO UTC instants, except `date`, which is the NHL's `America/New_York` slate day. Native formats instants locally. Reject unknown query parameters and oversized bodies rather than creating arbitrary cache keys.

| Method and resource | Response / behavior | Access |
| --- | --- | --- |
| `GET /scoreboard` | `ScoreboardReading` (`date`, games, `updatedAt`, `invalidatedAt`, `heardAt`); today's slate only in release one | Public |
| `GET /games/:id` | `GameSnapshot` (header, delayed, archived, plays); map `notFound` to 404 | Public |
| `GET /games/:id/prediction` | Existing `StoredPrediction`, or explicit pending/unavailable state respecting current eligibility; expose no private model inputs | Public |
| `GET /teams`, `GET /teams/:id`, `GET /teams/:id/schedule` | Existing team schemas; team schedule supports one season, not an unbounded history | Public; schedule can follow pilot |
| `GET /players?q=...`, `GET /players/:id` | Existing search and profile shapes; search is a bounded upstream result with `truncated` if capped, never invented pagination | Public |
| `GET /standings` | Existing standings schema | Public; after pilot |
| `GET /me`, `GET /me/favorites` | Application account summary and ordered team/player id lists | Session |
| `PUT /me/favorites/:kind/:id`, `DELETE /me/favorites/:kind/:id` | Idempotent add/remove, not toggle; enforce existing 24-per-kind cap and documented oldest-item eviction | Session |
| `GET /me/subscriptions`, `PUT /me/subscriptions/:kind/:id`, `DELETE /me/subscriptions/:kind/:id` | Per player/team/game enabled event types, enabled flag and `enabledAt`; favorites alone never enable push | Session |
| `GET /me/notification-settings`, `PUT /me/notification-settings` | Global enable, IANA time zone and quiet-hours interval | Session |
| `PUT /me/devices/:installationId`, `DELETE /me/devices/:installationId` | Register/rotate or disable this installation's Expo token; return registration id/status, never the token in a list | Session |
| `POST /me/children`, `POST /me/children/:id/password-reset` | Parent provision/recovery workflow below; owned children only | Parent session with recent reauthentication |

Single-resource success: `{ data, meta: { fetchedAt, sourceUpdatedAt, stale } }`; collections: `{ data: [...], page: { nextCursor }, meta }`. `fetchedAt` is when the server answered, never a claim of upstream freshness; unknown `sourceUpdatedAt` is null. Preserve delayed/last-known state and show it honestly. An empty search is a successful empty array; unavailable upstream data with no retained value is 503. A pending archive is an explicit state, not an invented final Replay.

Only growing persisted lists (subscriptions, later archived-game history) use cursors: default 25, maximum 100, stable `(createdAt,id)` keyset, opaque validated cursor bound to filters and account, no count query or offsets. The current slate and team directory are complete bounded collections (`nextCursor: null`). Live plays remain a whole snapshot for correctness; a future history cursor must pin an archive revision so corrected plays cannot move between pages unnoticed.

Errors are `{ error: { code, message, requestId, fields? } }`: 400 invalid input/cursor, 401 no valid session, 403 forbidden role, 404 absent resource (also another account's private resource), 409 conflicting/idempotency-key reuse, 429 rate limited with `Retry-After`, 503 unavailable source, 500 unexpected failure. Return stable codes and safe messages without stack traces or provider payloads. A timed-out create/reset uses a persisted `Idempotency-Key` scoped to parent and operation; retry reconciles the provider account using the preallocated application id instead of creating another child.

Public metadata can use ETags and private client revalidation; initially set downstream `Cache-Control: no-cache` and rely on the shared server cache so a second CDN TTL cannot outlive final invalidation. Live scores/game snapshots and predictions use `no-store` for the pilot. Private/account/auth responses always use `private, no-store`; no cache lookup occurs before authorization. API failures are not cached. A later edge cache requires measured benefit and the same invalidation contract as web.

Native sends a short-lived Clerk session bearer token to private resources. Use official backend session verification, issuer/signature/expiry and intended audience/origin configuration, then load the application account and its current parent/child authorization; never trust a body `userId` or editable client metadata. Web may use provider cookies through its server adapter, retaining origin/CSRF protection on mutations. CORS allows only known web origins and necessary headers; it is not native authentication. Public routes and sockets remain usable without an account. [Clerk verification](https://clerk.com/docs/reference/backend/verify-token).

Keep v1 additive: optional fields may be added; no meaning, required-field or enum changes for installed clients without an explicit compatibility strategy. Validate at the client boundary, tolerate unknown optional fields, and display a supported fallback for new statuses. Breaking changes get v2 alongside v1, not a forced same-day mobile update. Keep contract fixtures for the oldest supported app through backend deploys. Hono's inferred client is a developer convenience over this JSON contract.

## Existing WebSocket contract and native lifecycle

Connect to `wss://hockey.yogan.dev/agents/scoreboard-agent/main` and, only for the visible game, `/agents/game-agent/:id`. These are existing SDK routes, not a new multiplexed subscribe/unsubscribe service. Opening/closing a connection is the subscription. Use the Agents client SDK, pinned to a tested version compatible with server `agents@0.26.0`, instead of writing a second decoder for SDK framing. Cloudflare documents `AgentClient` for non-React clients and automatic reconnection; Metro/React Native compatibility still needs the device spike in ticket 1. [Client SDK](https://developers.cloudflare.com/agents/communication-channels/chat/client-sdk/).

| Stream | Existing message behavior | Native handling |
| --- | --- | --- |
| Scoreboard | SDK state is `ScoreboardState`; custom `{ type: "scoreboard_heard", at }` advances freshness on a successful unchanged poll | Full state replaces state; use the later of `updatedAt` and heard time. `invalidatedAt` invalidates cached team/player/pick queries. It is not a replay sequence number. |
| Game | SDK state is `GameStreamState`; custom `plays`, `play-added`, `play-changed`, `play-removed` follow `GameStreamMessageSchema` | Apply the shared reducer in received order. Each connect supplies all plays, including archived D1 plays; replace the old list on `plays`. Never assume plays are append-only. |

Current sockets are public and `shouldConnectionBeReadonly()` is true. Do not add client setters, exposed mutation RPCs, auth tokens in query strings, or account preferences to public state. Readonly is not authorization for future private data; any later private stream needs authenticated upgrade and account-scoped routing. [Cloudflare readonly connections](https://developers.cloudflare.com/agents/runtime/communication/readonly-connections/).

Start with REST first paint, then the socket; once socket state arrives, a late REST response cannot overwrite it. On reconnect, discard any partial old delta sequence and await the new full play list. Existing protocol has **no revision/cursor/replay log**; do not invent resume acknowledgements. State and plays arrive separately, so show “updating” until the new connection has delivered both. Buffer connection-local deltas until its full `plays` snapshot; ignore callbacks from disposed connections. A malformed required frame triggers a fresh snapshot/reconnect, not silent partial play application. Any future ordering/revision extension must update web and native compatibly first.

Own one Scoreboard connection at the native root while foregrounded and at most one Game connection. Close both on background/unmount; stop retries while offline; reconnect/refetch on active/network recovery with capped jittered backoff and no duplicate reconnect loop around the SDK. Keep last known scores with their timestamp, show reconnecting after the existing four-second grace, and distinguish Game's `delayed` flag (upstream failure). Reconcile the archive state with D1 before presenting Replay data. Background pushes are independent of these sockets; mobile background execution is not a reliable live transport.

## Notifications: preferences, observation and delivery

Use `expo-notifications` and Expo Push Service for ordinary iOS/Android alerts. Expo credentials and permission setup require a development/distribution build, plus testing on the target devices; Expo Go is not the acceptance environment. [Expo setup](https://docs.expo.dev/push-notifications/push-notifications-setup/).

**Initial event semantics:** player subscriptions receive goals credited to that athlete as `scorer`; team subscriptions receive that team's goals and its game finals; game subscriptions receive either side's goals and the final. Assists, penalties, shots, reminders, and goalie alerts can follow after the corresponding fixture coverage. Filter using `Play.scoring`, `participants[].athleteId/role` and `teamId`, not text matching; omitted athlete roles mean no player-specific claim. Shootout scoring is a separate play circumstance, not an ordinary goal total: omit it from player/team goal alerts in release one, while the final result still arrives. One event matching a player, a team and a game produces one user notification.

Favorites and notification subscriptions are distinct. Creating a subscription starts at its `enabledAt`, never replays a game's history. All push is opt-in after an explanatory in-app action; OS denial leaves scores usable. Parent and child can disable alerts; only the parent relaxes child quiet hours. Default quiet hours are 21:00–07:00 in the account's explicitly confirmed IANA zone, including across midnight/DST. Recheck settings and current ownership immediately before send. Suppress goals in quiet hours; optionally retain one latest final per game until quiet hours end, with a 12-hour expiry. Do not dump a night's goal backlog in the morning.

**Observation demand is the launch decision.** Extend the existing Agents' polling condition to “a foreground viewer OR an active notification lease.” Reuse one poll loop per existing object; never open hidden sockets or create a push worker that independently polls ESPN. Proposed bounded coordinator work refreshes watched-player team membership and relevant schedules through shared cached readers daily and on preference changes, schedules wakeups 15 minutes before relevant games, and reconciles postponed/start-time changes while the lease is active. Missing player team membership is shown as unable to schedule player alerts, not inferred from an old club. Recheck membership when the game window opens; prove traded-player behavior in fixtures.

The Scoreboard retains its single authoritative slate and cadences. Interested Game Agents retain their current 10-second play / 30-second intermission cadence, with leases ending at final plus existing archival work; a six-hour scheduled-start deadline bounds a stuck/postponed lease and records an operational failure for review. Renew only while the game is confirmed live, with an explicit bounded extension policy in the implementation ticket. With no viewers or leases, polling stops as today. This changes ADR 0007 and the glossary's viewer-only Game Stream definition; a later implementation ADR must record the accepted exception, resource budget and kill switch. Until approved, the pilot cannot promise alerts while everyone has closed the app.

**Durability:** detect candidate events in the same successful Agent poll that stores new state/plays. Persist an outbox record with the state change in the object's storage before advancing the observed baseline; drain idempotently into D1 and schedule retry independently of viewers. An upstream outage must not turn old catch-up history into new alerts: seed a baseline on first activation and persist a last-successful-observation watermark with each accepted snapshot. Before advancing that watermark, compare the previous success with the recovery poll against a proposed two-minute freshness budget. After a longer gap, suppress newly discovered plays with absent or unreliable `wallclock` and incorporate them into the recovered baseline; first-observed time alone cannot establish freshness. A newly discovered play with a reliable event timestamp is eligible only if that timestamp is within the freshness budget and after subscription/lease activation. Resume alerts for timestamp-less additions only on subsequent healthy observations within the budget. Persist the recovered baseline and watermark together so a restart cannot replay suppressed goals. The freshness check also runs before delivery; recovery does not extend an event’s expiry. Treat `play-changed`/`play-removed` as corrections: cancel unsent events or update their content; already-delivered goals cannot be recalled and do not trigger a second goal alert.

Persist unique canonical event keys `(gameId, playId, goal)` or `(gameId, final)` and unique recipient deliveries `(eventKey, accountId, installationId)`. New subscriptions cannot retroactively match older events. Poll retries, deploys and overlapping subscriptions must hit the same uniqueness constraints. State/outbox transaction tests and retry reconciliation are required; a network call to Expo is never part of that transaction.

**Device and delivery lifecycle:** registration upserts `(project, installationId)` for the authenticated account, platform, permission status, token and last-seen time. Token rotation disables the old token; reinstall produces a new installation. Enforce token uniqueness within a project and authorized reassignment on account switch. Logout disables that account's registration before removing credentials, with a retryable local logout cleanup if offline; account deletion disables all deliveries and removes tokens. Expire unused registrations after a proposed 30 days unless refreshed. Never log push tokens, credentials or child identity in operational events.

The sender claims due D1 delivery rows with an expiring lease, validates preferences/device again, sends bounded batches, persists returned ticket ids and polls receipts. Retry transient failures with exponential backoff/jitter and an expiry; disable tokens on `DeviceNotRegistered`; record permanent payload/credential failures for the operator. Expo tickets acknowledge acceptance, receipts describe downstream handoff, and neither proves display. Expo provides at-least-once handoff, so exactly-once visible delivery cannot be promised after an ambiguous send timeout. Include an event id for app-side deduplication and safe internal game deep links. Use push access-token protection and keep credentials in Worker secrets. [Sending and receipts](https://docs.expo.dev/push-notifications/sending-notifications/), [delivery guarantees and limits](https://docs.expo.dev/push-notifications/faq/).

Implement delivery retry/receipt timers with a small dedicated delivery Durable Object in this Worker and D1 as the durable ledger. It sends notifications but never reads ESPN. A scheduled recovery sweep reclaims expired work after a crash. Measure queue age, attempted/accepted/failed/expired counts and upstream delay. Use a fixture sender during development and a global push-disable switch for rollout. The existing `EspnAlert.announce()` reports operational ESPN failures; it is not the sports-event source.

## Child accounts: Better Auth versus Clerk

No earlier auth investigation artifact was found in this repo or its issues. This is a fresh primary-source comparison, not a claim that an earlier decision exists. Neither provider is installed today.

| Concern | Better Auth | Clerk |
| --- | --- | --- |
| Username/password | Username plugin signs in by username, but documented signup still requires a unique email and name. It does not provide email-free child creation by itself. [Username plugin](https://better-auth.com/docs/plugins/username). | Supports username as an identifier and password auth. Backend creation can omit email if instance settings do not require it; required fields follow instance configuration. [User model](https://clerk.com/docs/guides/users/managing), [configuration](https://clerk.com/docs/guides/configure/auth-strategies/sign-up-sign-in-options), [createUser](https://clerk.com/docs/reference/backend/user/create-user). |
| Expo | Official plugin stores sessions/cookies through SecureStore; custom API requests need the documented cookie forwarding. [Expo integration](https://better-auth.com/docs/integrations/expo). | Official Expo SDK includes secure token caching. Use a custom child username form and provider session management. [Expo quickstart](https://clerk.com/docs/expo/getting-started/quickstart). |
| Server/storage | Supports SQLite/D1 and Drizzle, with Hono integration. We own migrations, secrets, recovery, rate limiting and security updates. Verify the chosen adapter's D1 behavior rather than assuming interactive transactions. [SQLite/D1](https://better-auth.com/docs/adapters/sqlite), [Drizzle](https://better-auth.com/docs/adapters/drizzle), [Hono](https://better-auth.com/docs/integrations/hono). | Managed identities, credentials and sessions; D1 retains app relationships and preferences. Requires provider availability and a production configuration/cost review; no price assumption is made here. |
| Parent recovery | Admin plugin can set a user's password, but it requires privileged authorization. A parent must never become a global auth administrator. A scoped server recovery workflow is still application work. [Admin plugin](https://better-auth.com/docs/plugins/admin). | Worker Backend API can update a password and sign out active sessions. Parent ownership checks remain ours. [updateUser](https://clerk.com/docs/reference/backend/user/update-user). |

**Recommended identity flow (Clerk):** bootstrap Ryan as the first allowed parent with a real, verified adult email; no open parent role signup. Configure username/password and optional email globally, with the application requiring verified email for parent enrollment. The authenticated parent chooses the child's private username and initial passphrase. Hono authorizes parent creation, allocates an application account id, creates a Clerk user with username/password and no email, and commits an ownership link in D1. Keep a recoverable provisioning state across provider/D1 failures; an unlinked identity cannot access private app resources. The child enters only username/password on the native sign-in screen and can remain signed in using secure token storage. Do not store the password or expose a searchable child directory.

**Recovery:** “Ask your parent” is the child's recovery path; no security questions, public username lookup, or email sent to a fabricated address. The parent reauthenticates, selects an owned child, and submits a new passphrase over TLS. Hono checks the current parent-child link, rate limits and audits the action, calls Clerk's password update with session sign-out enabled, then invalidates app device registrations and cached private data. Apply an application revocation cutoff to private API access so already-issued JWTs cannot keep accessing the account until expiry. Test partial failures and do not report recovery complete until provider reset and revocation state agree. The child signs in again and separately re-enables device registration. The parent recovers their own account using the verified adult channel.

Avoid disabling provider password checks for child convenience; offer a readable passphrase and reveal/hide control. Use an app account id distinct from provider ids; role and parent links are server-owned. Parent approval records, account deletion (including provider identity, links, preferences, tokens and pending deliveries) and credentials redaction are acceptance criteria. No real child name, birth date or school is needed for this pilot. Public child enrollment or public store distribution needs a separate product/privacy review; this document makes no legal eligibility determination.

If Ryan instead prioritizes storing auth in D1, use Better Auth after the auth proof ticket: assign each child a unique private internal email-shaped identifier under a controlled non-delivering subdomain, distinct from the guardian's verified mailbox. Never reuse one parent's email on multiple child identities or pretend the internal alias proves email ownership. Disable email login/reset/verification delivery for child aliases; a scoped parent recovery service must use supported library APIs and revoke sessions without granting parents admin access. Prove alias handling, provider hooks and privileged recovery in workerd before adopting this alternative. This extra identity adaptation is why Clerk is the pilot recommendation, not because Better Auth lacks Expo or Workers support.

## Native Home and device widgets

Add `apps/native` with Expo Router, the supported Expo/React Native/React versions chosen together, and shared domain/contracts imports only. The web currently pins React 19.3.0; do not force it onto Expo independently of the selected SDK's compatibility requirements. Expo documents pnpm monorepos and Metro support, but duplicate React/native module resolutions must be checked in the real build. [Expo monorepos](https://docs.expo.dev/guides/monorepos/).

Home opens to a compact squared score ledger: local date, stable rows with away/home marks and scores, period/clock or start time, favorite mark, and the existing pick with explicit unavailable state. A favorite-player section links to profiles and an explicit alert control. Game opens score/status and readable plays; profile shows season information and team. Include visible Home, Favorites and Settings navigation, large touch areas, Dynamic Type/font scaling, screen-reader labels, contrast in both themes and no color-only status. Carry Geist-style interface and monospaced numeric hierarchy where the font license/build permits, using the approved tokens and aligned web screenshots as the reference, not literal desktop CSS measurements.

A device home-screen widget is a separate surface. Current `expo-widgets` docs describe iOS widgets/Live Activities with an isolated SwiftUI-based runtime; the app's React state and hooks do not run inside it. Remote Live Activity updates require APNs work beyond ordinary Expo alerts. [Expo widgets](https://docs.expo.dev/versions/latest/sdk/widgets/). Android widgets need separate platform investigation; this source is not evidence of cross-platform widget parity. Default: defer widgets until Ryan confirms platform and whether he wants a periodically refreshed favorite-team tile or an actively updated game. A future widget reads a bounded cached score snapshot with a visible timestamp and tap-to-open; it never polls ESPN or promises the app's 10-second foreground cadence.

## Decisions to carry into the PR

Recommended defaults: one existing Worker with Hono v1; shared domain/cache functions; current Agents protocol with full reconnect snapshots; Clerk parent-provisioned child usernames; opt-in goal/final alerts through Expo; app Home first, device widgets later. Documented assumptions are an invite-only family pilot, both native platforms with the first device chosen later, and bounded notification leases requiring Ryan's decision. No provider, preview, deployment, store submission or implementation ticket is created by accepting the plan.
